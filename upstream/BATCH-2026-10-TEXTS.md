## 1. `zig-pr-confidence`

**Title:** config: TF_FLASHNEXT_CONFIDENCE=-0.15 on one Spark (prose decode +7 to +10%, replies unchanged)

**Body:**

## Description and Motivation

`scripts/config.sh` now sets `TF_FLASHNEXT_CONFIDENCE=-0.15`. Before, it was unset, so the engine used its own
`-0.4`: the running-product draft stop, applied while at most `TF_FLASHNEXT_PRODUCT_STREAMS` (2) streams are live. The

| prose, 1 / 2 / 4 clients | 61.2 / 50.1 / 36.5 | 67.4 / 53.5 / 37.3 | +10.1 / +6.8 / +2.2% |

At four clients the per-draft rule applies in both arms, so those cells compare the same setting (code at four

## 2. `zig-pr-argmax`

**Title:** patches/0010: argmax and logsumexp row maxima on 1024 threads (replies byte-identical)

**Body:**

## Description and Motivation

`patches/0010-flash-next-argmax-lse-rows.patch` changes two launches in the Zig engine:

- `Torch.argmax` (the greedy pick over a vocabulary row, `tf_argmax_rows_i32_kernel`) launches 1024 threads a row
  instead of 256. The kernel is already `__launch_bounds__(1024)` and reduces through a 32-warp shared table.
- `tf_fn_lse_max_kernel` (the row maxima before logsumexp) takes up to 1024 threads (its shared table grows from 256 to
  1024 floats) with four loads in flight a thread, and launches with 1024.

Each launch is one block a row. With 256 threads a block reads a 248,320-column bf16 row at about 8 GB/s: the profile
(nsys, one stream) showed `tf_argmax_rows_i32_kernel` at ~60 us a call and `tf_fn_lse_max_kernel` at ~49 us. At four
streams the draft sampling (`mtp.draft_sample` in `TF_FLASHNEXT_PROFILE=1`) took ~1.5 ms a round.

Why the results do not change: the argmax pick is a total order (the first maximum, a NaN first, `argmax_order.h`), and
a maximum does not depend on which thread reads which column. The sums after the maxima (`tf_fn_lse_sum_kernel`) are
not touched, so logsumexp keeps ATen's reduction order.

Measured on one DGX Spark through the recipe's own server, defaults otherwise. Per-request decode tok/s, greedy,
thinking off, 512-token replies; the control is the same source rebuilt without the patch, so the build adds nothing:

| | control | 0010 |

| prose, 1 / 2 / 4 clients | 62.2 / 50.8 / 37.2 | 62.4 / 51.1 / 37.4 |

Small (+0.3 to +1% where the arms are steady; code at four clients varies between boots), but every cell moves the same
way and it costs two constants.

## 3. `zig-pr-mtp-fp8`

**Title:** patches/0011 + MTP_FP8: the MTP draft layer on block FP8 (code decode +4 to +5%, replies unchanged)

**Body:**

## Description and Motivation

INT4-AutoRound keeps the MTP layer (`mtp.layers.0`, the mixer) in bf16. Every draft step reads its attention
q/k/v/o and its three hyper-connection down/up pairs, ~139 MB, at the bf16 roofline: in `TF_FLASHNEXT_PROFILE=1` the
MTP head was ~12% of a one-stream round and ~15% at four streams, and its attention projection alone ran at ~213 GB/s
(nsys). This PR drafts from a block-FP8 copy of those linears, ~70 MB a step.

- `patches/0011-flash-next-mtp-fp8-overlay.patch`: `TF_FLASHNEXT_MTP_FP8=DIR` opens a second overlay directory, read
  before the checkpoint's `fast-fp8/` (that one repeats the MTP layer's bf16 tensors, so the first overlay holding a
  name wins). The MTP layer takes `attention8` when its `q_proj` is FP8 there; its hyper-connections already take the
  FP8 path when `input_mix_weight_down` is. The forward code is unchanged: the main layers' FP8 paths run.
- `tools/mtp_fp8.py`: writes the overlay. Each linear becomes e4m3 codes plus fp32 `weight_scale_inv` per 128x128
  block (scale = block amax / 448), the checkpoint's own block-FP8 format. Relative error ~2.6% a matrix.
- `scripts/prepare.sh` runs it once in the image into `$HF_CACHE/tensorfold-mtp-fp8/<model>/<revision>/` (as the
  user, no network), `start.sh` passes `TF_FLASHNEXT_MTP_FP8` when `MTP_FP8=1` and `DRAFTS=1`, and `prepared_state`
  includes the overlay, so a missing one re-runs `prepare.sh`. `MTP_FP8=0` drafts from the bf16 layer as before.

Why replies do not change: the MTP head only proposes drafts; the target model verifies every one and keeps only
what it would have produced. Only acceptance could move, and it did not measurably (decode rounds a pass within boot
noise of the bf16 arm).

Measured on one DGX Spark through the recipe's own server, defaults otherwise. Per-request decode tok/s, greedy,
thinking off, 512-token replies, medians of two boots an arm; the control is the same source rebuilt without the
patch, so the build adds nothing:

| prose, 1 / 2 / 4 clients | 62.0 / 50.7 / 37.3 | 63.3 / 51.5 / 38.0 | +2.1 / +1.6 / +1.9% |

## 4. `qwen-pr-copy-first`

**Title:** Patch 0012: copies from the context before MTP chains (TensorFold #319 ported to v0.6.1): a verbatim repeat 153.8 -> ~535 tok/s, same replies

**Body:**

## Description and Motivation

TensorFold #319 by @Arminova made Flash Next on CUDA try a copy from the context before the MTP chain. A reply that repeats its prompt, such as an agent quoting or rewriting a file it just read, otherwise keeps only a few tokens a round. #319 was written for TensorFold 0.6.4 and closed unmerged. This patch ports it to the recipe's v0.6.1, on top of 0002.

What it does, as in #319:

- On one GPU, a round first verifies a copied continuation when the context repeats eight or more tokens (TensorFold's `CopyIndex` from the Qwen3.5 27B engine), else the MTP chain.
- A copy's window starts at 16 rows, doubles while copies land whole (up to 64) and halves after a break (`copies.Copies`, on the 27B engine's `next_copy_rows`).
- With `PARALLEL` >= 2, every stream keeps its chain's rows (depth + 1). Copies share the rest of a round's max(`PARALLEL` x (depth + 1), 64) rows, oldest stream first (`copies.fit`). Every slot's replay rows hold 64, and the admission counts them (`indexed_stream_geometry(rows=, scratch=)`).
- A round's tokens join each stream's context before its next drafts, so `take` runs before `_draft_all`.
- Two ranks keep MTP chains only.

It replaces 0002's copy drafts, the `TENSORFOLD_MTP_COPY` path in `MultiDecoder._draft_all`. So that setting leaves `scripts/config.sh` and the README: copies are on whenever MTP drafts are, on one GPU. `tools/test_copy_draft_rows.py` tested that old path (it already fails on main, with `'SimpleNamespace' object has no attribute '_mtp'`), so this PR removes it. `tools/copy_first_check.py` covers the new path.

Measured on one DGX Spark through the server, against the recipe's own image:

| Reply | Before | After |
| --- | ---: | ---: |
| repeats its prompt word for word | 153.8 tok/s | ~535 tok/s (+248%) |
| a one-word rewrite of its prompt | 141.4 tok/s | ~322 tok/s (+128%) |

Prose, code and prefill stayed within noise. #319's own numbers, on 0.6.4: a file rewrite 3.7x faster (92.4 -> 341.0 tok/s with one stream, 92.9 -> 340.3 with `--parallel 5`).

The bits do not change. Copies are drafts, and every drafted token is checked against the model's own sample, as before.

Memory: the startup estimate at the defaults (5 x 262,144, int8) goes from 85.39 GiB (the README's v0.6.1 figure) to 85.81 GiB, within a 115.52 GiB budget on our Spark. The admission formula's own difference is 0.42 GiB: 9.356 -> 9.776 GiB at 262,144 tokens, from `indexed_stream_geometry` on the checkpoint's config.

## 5. `qwen-pr-ple-page-cache`

**Title:** Patch 0013: decode +9 to +12% with the n-gram tables on SSD: cached reads on the engine thread, the next round's rows hinted to the page cache

**Body:**

## Description and Motivation

With `PLE_ON_SSD=1`, every decode round's `stage()` reads its n-gram rows from the checkpoint files through `SSDTable.gather`. Every read went through a pool of 16 Python threads. An in-process profile of steady decode on prose showed these gathers leaving the GPU idle for 3.6 / 8.0 / 10.0% of decode time at 1 / 2 / 4 streams. The cause was the threads, not the disk. Each read cost about 9 us of handing work between threads under the GIL, against about 0.4 us for the read itself when its page is cached, so a decode window's gather took ~1.3 ms even with every page cached.

This patch changes two things:

- `SSDTable.gather` does a decode-sized gather's reads (up to 4,096) on the calling thread first, with `RWF_NOWAIT`. A read the page cache holds completes there; a read that would wait on the disk, or the rest of a partly cached one, goes to the threads as before. Larger gathers (prompt pieces) go to the threads as before.
- `MultiDecoder` hints the next round's rows with `POSIX_FADV_WILLNEED`, on one helper thread, while the GPU runs the MTP steps: each stream's first token after the accept, each copy (0012), then each draft as the chain picks it. `SSDTable.will_need` advises exactly each row's three parts.

The bytes do not change. Both paths read the same file bytes; a hint only starts a page read early.

`TENSORFOLD_PLE_NOWAIT=0` sends every read to the threads again, and `TENSORFOLD_PLE_HINTS=0` turns the hints off. `start.sh` already passes `TENSORFOLD_*` variables into the container. With the tables in memory (`PLE_ON_SSD=0`) nothing changes.

Measured on one DGX Spark through the server, interleaved A/B, 3 passes an arm, median tok/s a request (the pass spreads did not overlap):

| Workload | 1 stream | 2 streams | 4 streams |
| --- | ---: | ---: | ---: |
| prose, before | 66.2 | 45.6 | 28.4 |
| prose, after | 73.9 | 50.1 | 31.9 |
| code, before | 77.7 | 58.8 | 36.9 |
| code, after | 85.1 | 64.0 | 41.0 |

That is +9 to +12% in every cell. Every reply in the A/B was byte-identical.

`0013` is a placeholder. This PR depends on #<0012 PR> (copy-first): its `multi.py` hunks sit in 0012's `_draft_all`. Patches 0014 and 0015 build on this one.

## 6. `qwen-pr-ple-native`

**Title:** Patch 0014: prefill with the n-gram tables on SSD +47% at 8k: the table reads in native threads, the same bytes

**Body:**

## Description and Motivation

With `PLE_ON_SSD=1`, every n-gram lookup reads its rows from the checkpoint files: one `pread` per run of adjacent rows, for the words, scales and biases. After 0013 a decode window's cached reads run on the engine thread, but a prompt piece's reads still go through 16 Python threads, and each read still costs Python work under the GIL. A 2,048-row piece holds 32,768 n-gram ids and needs tens of thousands of reads. In-process, an 8k-token prompt left the GPU idle for 31% of its prefill while it waited for these reads.

This patch builds the same reads as a table (file, offset, length, place in one output buffer) and hands it to a small C++ extension, built once at startup with `torch.utils.cpp_extension.load_inline` into the kernel cache. The extension does every `pread` in native threads with the GIL released: one thread up to 1,023 reads (a decode window), then one per 512 reads, up to 64 (a cold prompt piece waits on the disk, so more reads in flight). The rows are then taken in the same order as before.

The bytes do not change: the same files, offsets and lengths, read into the same rows. `TENSORFOLD_PLE_NATIVE=0` restores the Python reads. They are also the fallback, with one line on stderr, if the extension cannot build.

Measured on one DGX Spark:

- One gather of 16,384 ids, warm pages, best of 5: 232 -> 9.5 ms.
- Through the server, interleaved A/B, 3 passes an arm, every boot from a cold n-gram table, median tok/s (range):

| Prompt | Before | After |
| ---: | ---: | ---: |
| 8k | 1,735 (1,626-1,907) | 2,547 (2,545-2,549) |
| 32k | 2,354 (2,354-2,449) | 2,637 (2,632-2,640) |
| 128k | 2,230 (2,229-2,246) | 2,297 (2,293-2,301) |

## 7. `qwen-pr-chain-stop`

**Title:** Patch 0015: TENSORFOLD_CHAIN_RULE, where an MTP chain stops (cum: +5.5% for one stream writing code, +1.4% on average, same replies)

**Body:**

## Description and Motivation

v0.6.1 ends a round's MTP chain at the first draft whose draft-head probability is under `--mtp-confidence`. A static sweep of depth (3-8) and confidence (0.5-0.8) on real prose and code found 6 / 0.60, the recipe's default, the best single setting: prose wants short permissive chains, code long ones. One threshold on one draft's probability cannot serve both, and the draft head is overconfident: a draft it gives 0.5 lands about 41% of the time, 0.85 about 71%, 0.99 about 95%.

This patch adds `TENSORFOLD_CHAIN_RULE`:

- `conf` (the default): v0.6.1's rule, unchanged.
- `cum`: each draft's probability is mapped through a measured landing curve (`CAL`, 14 points; greedy, real prose and code, every chain run to depth 8, 4,935 tested drafts). The chain stops once the chance that every draft so far lands, the product of those calibrated values, falls under `TENSORFOLD_CHAIN_T` (default 0.30). The first draft is always kept, as in v0.6.1.
- `cost`, `adapt`, `acum`: experimental. `cost` keeps a draft while its chance buys more than a verify row's measured cost, and `adapt` / `acum` scale `cost` / `cum` by each stream's recent landing rate. They are not recommended; `cum` won.

Drafts change speed only, so every rule keeps the reply's bits: each drafted token is still checked against the model's own sample.

Measured on one DGX Spark through the server, on prompts the rule was not chosen on, interleaved A/B, 3 passes an arm, cold n-gram tables, median tok/s a request. "Before" is `MTP_DRAFTS=6` with `conf` (the recipe's defaults); "after" is `MTP_DRAFTS=8` with `TENSORFOLD_CHAIN_RULE=cum`:

| Workload | 1 stream | 2 streams | 4 streams |
| --- | ---: | ---: | ---: |
| code, before | 85.3 | 64.4 | 41.1 |
| code, after | 90.0 | 63.3 | 42.1 |
| prose, before | 74.2 | 50.5 | 32.1 |
| prose, after | 74.4 | 51.1 | 32.4 |

About +1.4% on average and +5.5% for one stream writing code. Code at 2 streams lost 1.7% a request while its aggregate rose from 122.8 to 123.9 tok/s. On the texts the rule was chosen and calibrated on (in-process, 14 rule arms x 3 passes, then the leaders x 4 fresh passes), it measured +1.3 to +6.1% in all six cells, mean +3.1%.

This PR leaves the default at `conf`. `TENSORFOLD_CHAIN_RULE=cum MTP_DRAFTS=8 ./start.sh restart` gives the numbers above (`start.sh` passes `TENSORFOLD_*` variables into the container). ## 8. `qwen-pr-mtp-graphs`

**Title:** Patch 0016: the MTP head's chain steps as CUDA graphs: decode +0.3 to +1.4% through the server, the eager step's bits

**Body:**

## Description and Motivation

A decode round drafts with up to `MTP_DRAFTS` MTP head steps. After the round's absorb, each step runs one row per chaining stream. Eager, such a step is ~40 kernel launches from Python, and its host time is close to its GPU time, so the GPU waits between steps. A trace of one stream's steady decode showed the GPU idle for 12% of it, with 15-60 us gaps before each kernel of an MTP step.

This patch adds `ChainGraphs`. A step of one row per stream, with no image stream, replays a CUDA graph of `mtp_compute`:

- Key: the stepping streams' MTP cache addresses (the attention's captured pointer table) and a power-of-two context bucket, at least 8,192. The attention's sparse select is launched for every stream with the bucket as its context. Its kernels read each row's real end from the device, so the extra blocks and chunks score, select and merge nothing, and a replay computes the eager step's bits.
- Per replay, only the rows' positions are uploaded, one pinned copy of the step's integer table.
- A key is captured the second time it is seen, so a one-off set of chaining streams stays eager. At most 32 graphs; the least recently replayed goes first.
- Steps of more than one row a stream, and image streams, stay eager.

`TENSORFOLD_MTP_GRAPHS=0` runs every step eagerly.

The bits do not change: a replay computes what the eager step computes, so the drafts, and therefore which drafts land, are the same. The replies are verified as before.

Measured on one DGX Spark through the server, interleaved A/B, 3 passes an arm, arm order rotated, cold n-gram table every boot, median tok/s a request:

| code, before | 90.2 | 63.6 | 42.1 |
| code, after | 91.3 (+1.2%) | 64.5 (+1.4%) | 42.4 (+0.7%) |
| prose, before | 74.6 | 51.0 | 32.2 |
| prose, after | 75.2 (+0.8%) | 51.5 (+1.0%) | 32.3 (+0.3%) |

Prefill was unchanged (8k / 32k / 128k: 2,548 / 2,634 / 2,301 -> 2,543 / 2,638 / 2,298 tok/s). ## 9. `qwen-pr-ple-defer`

**Title:** Patch 0017: a decode round's n-gram rows read while the GPU runs layers 0-1: with 0016, decode +1.8 to +2.2%, same bytes

**Body:**

## Description and Motivation

A decode round's `stage()` looks up every n-gram layer's rows, reads them (from SSD with `PLE_ON_SSD=1`) and copies them to the GPU before the forward starts. The GPU waits for all of it, although the first n-gram layer only comes after layers 0 and 1.

This patch adds `stage(..., defer_ple=True)`. The token ids still go up in `stage`, but the n-gram rows are looked up, read and copied when the forward reaches its first n-gram layer: `ple_block` runs the staging (`b.ple_staging`) before its first kernel, then records the stream's event. So the host reads the rows while the GPU runs the layers before it. The same bytes land in the same buffers ahead of the same kernels on the stream; nothing else changes.

A decode round alone defers. A round that shares its forward with a prompt pass stages the rows first, as before. `TENSORFOLD_PLE_DEFER=0` always stages them first.

The bits do not change, for the reason above.

## 10. `qwen-pr-tokenize-nogil`

**Title:** Patch 0018: no stall at a long request's start: the server tokenizes with Python's GIL released

**Body:**

## Description and Motivation

The server turns each prompt into ids with the tokenizer's `encode` (`App._prepare` for chat and completions, `App.decisions`, the forced think close and the tool-call gate). HF tokenizers' `encode` holds Python's GIL for the whole text: ~0.36 s at 256k tokens on the DGX Spark. The engine loop that schedules every stream's rounds runs in the same process, so while a long prompt is being tokenized, every other stream stops.

The ids do not change, so neither do the replies.
