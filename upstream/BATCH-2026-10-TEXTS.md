## 1. `zig-pr-confidence`

**Title:** config: TF_FLASHNEXT_CONFIDENCE=-0.15 on one Spark (prose decode +7 to +10%, replies unchanged)

**Body:**

## Description and Motivation

`scripts/config.sh` now sets `TF_FLASHNEXT_CONFIDENCE=-0.15`. Before, it was unset, so the engine used its own
`-0.4`: the running-product draft stop, applied while at most `TF_FLASHNEXT_PRODUCT_STREAMS` (2) streams are live. The
engine's comment says `-0.4` was tuned at TP=2. On one Spark longer chains pay off: with `-0.15` a chain stops once its
drafts' joint chance falls under 0.15 instead of 0.4.

Only where a chain stops changes. Every draft is still verified, so every reply stays byte-identical. Above two live
streams nothing changes (the per-draft rule at 0.5 applies there).

Measured on one DGX Spark through the recipe's own server, stock image `tensorfold-qwen38:zig-db28187`, defaults
otherwise. Per-request decode tok/s, greedy, thinking off, 512-token replies, prose and code prompts, medians of two
boots an arm:

| | stock (`-0.4`) | `-0.15` | change |
| --- | ---: | ---: | ---: |
| code, 1 / 2 / 4 clients | 103.8 / 75.5 / 53.0 | 106.5 / 76.1 / 52.8 | +2.6 / +0.8 / -0.4% |
| prose, 1 / 2 / 4 clients | 61.2 / 50.1 / 36.5 | 67.4 / 53.5 / 37.3 | +10.1 / +6.8 / +2.2% |

At four clients the per-draft rule applies in both arms, so those cells compare the same setting (code at four
clients moves a few % between boots on this box either way).

We swept the threshold first (-0.1, -0.15, -0.2, -0.25, -0.3 against -0.4, two or three boots an arm). Lower
thresholds help prose most; -0.1 and -0.2 traded about 2% between prose and code; -0.15 was the best balance.

it stays 2.

## 2. `zig-pr-argmax`

**Title:** patches/0010: argmax and logsumexp row maxima on 1024 threads (replies byte-identical)

**Body:**

## Description and Motivation

`patches/0010-flash-next-argmax-lse-rows.patch` changes two launches in the Zig engine:

- `Torch.argmax` (the greedy pick over a vocabulary row, `tf_argmax_rows_i32_kernel`) launches 1024 threads a row
  instead of 256. The kernel is already `__launch_bounds__(1024)` and reduces through a 32-warp shared table.
- `tf_fn_lse_max_kernel` (the row maxima before logsumexp) takes up to 1024 threads (its shared table grows from 256 to
  1024 floats) with four loads in flight a thread, and launches with 1024.

Each launch is one block a row. With 256 threads a block reads a 248,320-column bf16 row at about 8 GB/s: the profile
(nsys, one stream) showed `tf_argmax_rows_i32_kernel` at ~60 us a call and `tf_fn_lse_max_kernel` at ~49 us. At four
streams the draft sampling (`mtp.draft_sample` in `TF_FLASHNEXT_PROFILE=1`) took ~1.5 ms a round.

Why the results do not change: the argmax pick is a total order (the first maximum, a NaN first, `argmax_order.h`), and
a maximum does not depend on which thread reads which column. The sums after the maxima (`tf_fn_lse_sum_kernel`) are
not touched, so logsumexp keeps ATen's reduction order.

Measured on one DGX Spark through the recipe's own server, defaults otherwise. Per-request decode tok/s, greedy,
thinking off, 512-token replies; the control is the same source rebuilt without the patch, so the build adds nothing:

| | control | 0010 |
| --- | ---: | ---: |
| code, 1 / 2 / 4 clients | 104.7 / 76.1 / 52.2 | 105.3 / 76.8 / 54.1 |
| prose, 1 / 2 / 4 clients | 62.2 / 50.8 / 37.2 | 62.4 / 51.1 / 37.4 |

Small (+0.3 to +1% where the arms are steady; code at four clients varies between boots), but every cell moves the same
way and it costs two constants.

## 3. `zig-pr-mtp-fp8`

**Title:** patches/0011 + MTP_FP8: the MTP draft layer on block FP8 (code decode +4 to +5%, replies unchanged)

**Body:**

## Description and Motivation

INT4-AutoRound keeps the MTP layer (`mtp.layers.0`, the mixer) in bf16. Every draft step reads its attention
q/k/v/o and its three hyper-connection down/up pairs, ~139 MB, at the bf16 roofline: in `TF_FLASHNEXT_PROFILE=1` the
MTP head was ~12% of a one-stream round and ~15% at four streams, and its attention projection alone ran at ~213 GB/s
(nsys). This PR drafts from a block-FP8 copy of those linears, ~70 MB a step.

- `patches/0011-flash-next-mtp-fp8-overlay.patch`: `TF_FLASHNEXT_MTP_FP8=DIR` opens a second overlay directory, read
  before the checkpoint's `fast-fp8/` (that one repeats the MTP layer's bf16 tensors, so the first overlay holding a
  name wins). The MTP layer takes `attention8` when its `q_proj` is FP8 there; its hyper-connections already take the
  FP8 path when `input_mix_weight_down` is. The forward code is unchanged: the main layers' FP8 paths run.
- `tools/mtp_fp8.py`: writes the overlay. Each linear becomes e4m3 codes plus fp32 `weight_scale_inv` per 128x128
  block (scale = block amax / 448), the checkpoint's own block-FP8 format. Relative error ~2.6% a matrix.
- `scripts/prepare.sh` runs it once in the image into `$HF_CACHE/tensorfold-mtp-fp8/<model>/<revision>/` (as the
  user, no network), `start.sh` passes `TF_FLASHNEXT_MTP_FP8` when `MTP_FP8=1` and `DRAFTS=1`, and `prepared_state`
  includes the overlay, so a missing one re-runs `prepare.sh`. `MTP_FP8=0` drafts from the bf16 layer as before.

Why replies do not change: the MTP head only proposes drafts; the target model verifies every one and keeps only
what it would have produced. Only acceptance could move, and it did not measurably (decode rounds a pass within boot
noise of the bf16 arm).

Measured on one DGX Spark through the recipe's own server, defaults otherwise. Per-request decode tok/s, greedy,
thinking off, 512-token replies, medians of two boots an arm; the control is the same source rebuilt without the

| prose, 1 / 2 / 4 clients | 62.0 / 50.7 / 37.3 | 63.3 / 51.5 / 38.0 | +2.1 / +1.6 / +1.9% |

Code gains more because its chains run deeper (more draft steps a round, each reading the MTP layer).

## 4. `zig-pr-ngram-host`

**Title:** patches/0012: the n-gram table's host gather on a thread gang with read-ahead (cold prompts of new text 2-9x faster, replies byte-identical)

**Body:**

## Description and Motivation

At one GPU the engine keeps the FP8 n-gram (PLE) table host-mapped (`cuda_weights.zig` `openTable`; the
two-rank layout puts each rank's heads on the GPU) and gathers a window's rows on the engine thread, one row at a time
(`NgramTable.gather`). The table is `ple-table/`, 48.67 GiB in 34 files, and every token reads 16 rows of 160 B at
hashed offsets: 16 different 4 KiB pages. A page that is not in the page cache is a synchronous fault, and the kernel's
128 KiB read-around reads 32 pages for it: one 8k prompt of new text took the table from 2.8% to 24.9% resident (12 GiB
read for 17 MB of rows), each fault cost ~250 us on the serving thread, and the next request found its rows evicted
again. A GPU copy does not fit beside the weights on one Spark (48.67 GiB against 43.85 GiB free after load).

`patches/0012-flash-next-ngram-host-gather.patch` keeps the gather's bits (the same rows through the same LUT into the
same positions) and changes only when and on which thread the pages are read:

- `cuda_ngram_host.zig` (new): a gather of at least `TF_FLASHNEXT_NGRAM_MIN` (32) rows is split into blocks over
  `TF_FLASHNEXT_NGRAM_THREADS` worker threads plus the caller, so cold rows fault in parallel.
- `TF_FLASHNEXT_NGRAM_PREFETCH=1`: the same workers touch rows that will be gathered soon, in the background: during a
  prefill the next `TF_FLASHNEXT_NGRAM_AHEAD` (2) chunks while the current one computes; during decode the next
  window's pending token, and each draft as the MTP chain draws it.
- `TF_FLASHNEXT_NGRAM_RANDOM=1`: `MADV_RANDOM` on the table's mappings, so a miss reads its own page only.
- `scripts/config.sh` turns all three on (32 threads; 64 bought 0.1 s more at 8k on a 20-core Spark). Unset or
  `TF_FLASHNEXT_NGRAM_THREADS=0` is the engine's one-thread gather; the prefetch follows the thread count.
- The README's "the n-gram table is on the GPU" (Configuration) now says where it is at one Spark.

Why the replies do not change: the gang's blocks and the serial gather read the same rows into the same output
positions, and a touch only reads a byte of a row. Only the thread and the moment of each page read move.

Measured on one DGX Spark through the recipe's own server: arms interleaved, one boot and one pass an arm per cycle, the order reversed each cycle. Greedy, thinking off, per-request decode tok/s from the client (512-token replies unless a row says otherwise). Every arm ran with `patches/0010` and `0011` and the MTP FP8 overlay (#35, #36) and `TF_FLASHNEXT_CONFIDENCE=-0.15` (#34). The prompt cache was off and the table's pages dropped before each cold request, with new text every time
(a repeated prompt costs no faults at all). Lane image (this patch alone on the stock engine), two cycles:

| cold prompt of new text | stock | 0012 |
| --- | ---: | ---: |
| 8k prose, s | 25.8 / 19.4 | 2.98 / 2.98 |

| the same 8k / 32k warm, s | 2.70 / 11.1 | 2.70-2.75 / 11.1-11.5 |
| decode, 4 clients, new text, aggregate tok/s | 100.2 / 101.9 | 128.4 / 129.7 |

A cold prompt now takes within 1-10% of a warm one (stock: 2-10x the warm time). The stock decode of new text lost
12-15% at one client and 23-24% at four (warm: 131.8 / 132.3 aggregate); with the patch it is within 1-5%. In the
merged build (with `0013` and `0017`, which do not touch prefill): cold 8k 1,167 / 1,941 -> 2,818 / 2,904 prompt
tok/s, 32k 1,741 / 2,307 -> 2,861 / 2,867, decode 1 / 2 / 4 clients equal (code 118.1 / 84.2 / 54-58 -> 117.9 / 85.1 /
59.4).

Arms dropped on the way (measured): `MADV_RANDOM` alone halves the cold cost (8k 9.58 s) but leaves the faults
serial; the gang without the prefetch is 0.4-1.3 s a cold prompt slower (8k 3.42 s).

## 5. `zig-pr-copy-window`

**Title:** patches/0013: 64-row copy windows for a lone stream (file copies 2.3x, one-line edits +84%, replies byte-identical)

**Body:**

## Description and Motivation

A lone stream's verify window held 16 rows: the pending token and 15 drafts, whether the drafts came from
the MTP head or were copied from the context (a file being rewritten, a verbatim repeat). A copy that lands every row
could only grow 15 at a time.

`patches/0013-flash-next-copy-window.patch` separates the window from the MTP chain:

- `cuda_state.max_rows` and `cuda_lanes.max_rows` 16 -> 64, with every host array sized by them following (held
  rows, ids, the sampler's scratch, `Round.held_stride`, the draw tables). A prompt burst stays at `state.ends` (16)
  prompts.
- `Engine.Options.window` / `TF_FLASHNEXT_WINDOW` (depth + 1 .. 64; 64 when unset): the decode buffers hold
  `max(8, streams x (depth + 1), window)` rows (128 at `PARALLEL=8`, as before) and each sequence keeps `window`
  speculative rows past the context.
- The lanes keep `depth` (the head's chain, `TF_FLASHNEXT_DEPTH`) and `window` apart: the round planner's copy ramp
  still starts at 15 rows and now grows 15 -> 31 -> 63, the head still drafts 15 at most, and the planner's cost
  table is still timed for 1..16 rows. Shared rounds (two or more clients) still copy 15 rows (`0015` changes that).
- The server's boot log says `copy windows: a lone stream verifies up to 64 rows ...`; the window is part of the
  two-rank settings agreement.

Why the replies do not change: copies are drafts, verified row by row like the MTP head's, and every row kernel is
row-invariant (shared rounds already run 17..128 rows through the same kernels).

Measured on one DGX Spark through the recipe's own server: arms interleaved, one boot and one pass an arm per cycle, the order reversed each cycle. Greedy, thinking off, per-request decode tok/s from the client (512-token replies unless a row says otherwise). Every arm ran with `patches/0010` and `0011` and the MTP FP8 overlay (#35, #36) and `TF_FLASHNEXT_CONFIDENCE=-0.15` (#34). One client, lane image (the wide window on the stock engine), one hold (hold5: a warm-up boot first, then the
arms interleaved):

| --- | ---: | ---: |

| a rename to a longer name | 256 | 409-411 |

Prose and code decode at one and two clients stayed within 1% (28/28 decode replies identical), with the same round

## 8. `zig-pr-seq-pool`

**Title:** patches/0016: pooled sequences keep their CUDA graphs across requests (short replies 9% faster, replies byte-identical)

**Body:**

## Description and Motivation

Every request gets a new sequence and frees it at the end, and a solo window's CUDA graph bakes in its
sequence's buffers: a one-client server re-captures its decode graphs request after request (about 200 solo captures

`patches/0016-flash-next-sequence-pool.patch` (one GPU):

- `TF_FLASHNEXT_SEQ_POOL=N`: up to N finished sequences are kept for the next request (`Engine.takeSeq` /
  `retire`). A pooled sequence reserves the engine's whole window, so every request sees the same capacities and the
  graph keys repeat. Back in the pool it is reset to exactly what a new sequence is: physical memory past the first

## 13. `zig-pr-fill-fix`

**Title:** patches/0021: fix TF_FLASHNEXT_FILL=1 with two or more prompts at once (prompts fill one after another; a resume's MTP absorb waits for its own chunk)

**Body:**

## Description and Motivation

A correctness fix to the engine's opt-in sliced fill (`TF_FLASHNEXT_FILL=1`: prompts fill in slices of layers
between the other streams' rounds, so a long prompt does not stall the streams that are decoding). It is off by
default in the recipe, so a default install never takes this path; this PR changes no setting. The code it fixes is
the release's own (`patches/0005`: `fillBegin`, `fillStep`, `prefillStepFn`); the speed patches only made it visible.

**The bug.** With `TF_FLASHNEXT_FILL=1`, any two prompts that fill at the same time both fail. On our build every
concurrent request of a 2-client and a 4-client decode matrix came back empty after 0.02-0.04 s, while one client was
fine; the server log says `reason=error (PromptBuffersBusy) prompt=32 tokens=0 after=0.03s`.

- The engine has one set of prompt buffers (`Engine.pfill`), and a prompt chunk stays open over several `fillStep`
  slices (8 layers a step).
- `cuda_lanes.zig` `prefillStepFn` calls `fillStep` for every filling stream on each step. When two prompts fill at
  once (every barrier-started batch of 2+ clients), the second call returns `error.PromptBuffersBusy`, and
  `lanes.Engine.advanceFills` then fails every filling stream.
- One prompt filling beside streams that decode works, which is why a test of one decoder plus one filler passes.

A second, silent defect is on the same path: on a prompt-cache resume, `fillBegin` ran the MTP tail absorb
(`mtp.forward`) in the prompt buffers at once. If another prompt's chunk was open then, the absorb overwrote it and that
other request got a wrong reply, with no error.

**The fix** (`patches/0021-flash-next-sliced-fill-one-at-a-time.patch`):

1. `cuda_lanes.zig` `prefillStepFn`: while another fill holds the prompt buffers, a filling stream skips its slice and
   stays filling. Prompts that arrive together fill one after another, in arrival order.
2. `cuda_engine.zig` `fillBegin` / `fillStep`: on a resume, `fillBegin` parks the snapshot's tail row in the
   sequence's `last_streams` and marks the fill; `fillStep` runs the absorb (`mtp.forward` + `setMtpLen`) when it opens
   this fill's first chunk, after taking the prompt buffers. The order on the sequence is unchanged: restore, absorb,
   chunks. `fillBegin` now touches no prompt buffer.
3. The host tests' `Toy` engine now models the one set of prompt buffers, and a new test starts four streams before
   the first step and checks each against serial decoding.

## 14. `zig-pr-readout-12bit`

**Title:** patches/0022: decode read-outs from a lossless 12-bit copy of their weights (decode +2.6 to +3.7% at 1 client, replies byte-identical)

**Body:**

## Description and Motivation

At decode widths every layer's hyper-connection read-out reads two bf16 matrices (attention and MLP `down`
[low (+ the inject rows), wide] and `up` [wide, low]): ~1.27 GB a round over 192 matrices, run by Triton's split
`_b16mm` with #49's fused `_reduce` + `_hc_act`, and `_hc_up_mix`. Those reads are bandwidth-bound, and bf16 spends 8
bits a weight on an exponent that varies little within a row.

`patches/0022-flash-next-readout-12bit-weights.patch` (`TF_FLASHNEXT_HC_Q12=1`):

- At load, a GPU packer (`tf_fn_hc_q12_pack_kernel`) builds a lossless 12-bit copy of each main-layer read-out matrix
  from its loaded bf16 rows. Per (row, 64 k) the largest exponent is stored once as a base; each weight keeps its

## 15. `zig-pr-indexer-select`

**Title:** patches/0023: the sparse-attention indexer's block lists from one read of each row, and its prompt scores on fma.rn.f32.bf16 (cold prefill +4 to +9% at 100k-200k, decode -6.5% time a token at 200k; replies byte-identical)

**Body:**

## Description and Motivation

Flash Next's sparse attention first picks, for every row, the TOP key blocks by an indexer score (`_scores`), then
lists them in block order (`_select`, or `_select_tiles` past `_select`'s registers). At long contexts both grow with
the context: in an eager profile at 200k, decode select took 2.04 ms of a 47.8 ms round and the MTP steps' select 0.55
ms; a 2048-row prompt chunk spent 75.4 ms in `qsa_scores` and 40.8 ms in `qsa_select`.

`patches/0023-flash-next-indexer-select-scores-tile.patch`:

- `TF_FLASHNEXT_QSA_SELECT=1`: the block lists of decode windows, MTP steps and prompt blocks come from a new kernel
  file, `fn_qsa_stream.cu`. Each row's scores are read once, in block order, through a shared-memory candidate buffer
  that always holds the TOP best of the prefix seen so far (a later block must beat the current cut); an overflowing
  buffer is compacted by a 3-pass radix cut over the top 11/11/10 bits, and the last compaction emits the list in
  block order. Ties go to the lower block id, as in `_select`. Two kinds: `s5` (one 512-thread CTA a row) and `cs4`
  (a cluster of 4 CTAs a row, each cutting its slice to its own TOP, rank 0 merging them over distributed shared
  memory). Decode uses `cs4` from 32,768 blocks (~131k keys) and `s5` below; prompt blocks use `s5`. Off (`0`), the
  Triton kernels run as before.
- `TF_FLASHNEXT_QSA_TILE=4`: the prompt indexer's scores (`fn_qsa_scores.cu`, already in the engine) gain four tiles
  4-7 that compute the per-dim products with `fma.rn.f32.bf16` on the packed bf16 words, the PTX instruction
  `_scores` itself uses, in its order, instead of widening each operand to fp32 first. Tile 4 is the 2 x 4 shape.
- `qsa-check` also compares every `fn_qsa_stream` kind and every score tile with `_scores` / `_select` at decode
  windows (1, 3, 16 rows, bucketed and exact key counts, positions 2,045-261,000) as well as prompt blocks, and times
  them. The boot log says `qsa select: ...`.

ties included), and the score tiles compute the same fp32 words as `_scores` (`fma.rn.f32.bf16(k1, q1, -0.0)` equals
`mul.rn(k1, q1)` exactly, and bf16 widens to fp32 exactly).

## 19. `qwen-pr-ple-page-cache`

**Title:** Patch 0013: decode +9 to +12% with the n-gram tables on SSD: cached reads on the engine thread, the next round's rows hinted to the page cache

**Body:**

## Description and Motivation

With `PLE_ON_SSD=1`, every decode round's `stage()` reads its n-gram rows from the checkpoint files through `SSDTable.gather`. Every read went through a pool of 16 Python threads. An in-process profile of steady decode on prose showed these gathers leaving the GPU idle for 3.6 / 8.0 / 10.0% of decode time at 1 / 2 / 4 streams. The cause was the threads, not the disk. Each read cost about 9 us of handing work between threads under the GIL, against about 0.4 us for the read itself when its page is cached, so a decode window's gather took ~1.3 ms even with every page cached.

This patch changes two things:

- `SSDTable.gather` does a decode-sized gather's reads (up to 4,096) on the calling thread first, with `RWF_NOWAIT`. A read the page cache holds completes there; a read that would wait on the disk, or the rest of a partly cached one, goes to the threads as before. Larger gathers (prompt pieces) go to the threads as before.
- `MultiDecoder` hints the next round's rows with `POSIX_FADV_WILLNEED`, on one helper thread, while the GPU runs the MTP steps: each stream's first token after the accept, each copy (0012), then each draft as the chain picks it. `SSDTable.will_need` advises exactly each row's three parts.

The bytes do not change. Both paths read the same file bytes; a hint only starts a page read early.

`TENSORFOLD_PLE_NOWAIT=0` sends every read to the threads again, and `TENSORFOLD_PLE_HINTS=0` turns the hints off. `start.sh` already passes `TENSORFOLD_*` variables into the container. With the tables in memory (`PLE_ON_SSD=0`) nothing changes.

Measured on one DGX Spark through the server, interleaved A/B, 3 passes an arm, median tok/s a request (the pass spreads did not overlap):

| Workload | 1 stream | 2 streams | 4 streams |
| --- | ---: | ---: | ---: |
| prose, before | 66.2 | 45.6 | 28.4 |
| prose, after | 73.9 | 50.1 | 31.9 |
| code, before | 77.7 | 58.8 | 36.9 |
| code, after | 85.1 | 64.0 | 41.0 |

That is +9 to +12% in every cell. Every reply in the A/B was byte-identical.

## Description and Motivation

## 22. `qwen-pr-mtp-graphs`

**Title:** Patch 0016: the MTP head's chain steps as CUDA graphs: decode +0.3 to +1.4% through the server, the eager step's bits

**Body:**

## Description and Motivation

A decode round drafts with up to `MTP_DRAFTS` MTP head steps. After the round's absorb, each step runs one row per chaining stream. Eager, such a step is ~40 kernel launches from Python, and its host time is close to its GPU time, so the GPU waits between steps. A trace of one stream's steady decode showed the GPU idle for 12% of it, with 15-60 us gaps before each kernel of an MTP step.

This patch adds `ChainGraphs`. A step of one row per stream, with no image stream, replays a CUDA graph of `mtp_compute`:

- Key: the stepping streams' MTP cache addresses (the attention's captured pointer table) and a power-of-two context bucket, at least 8,192. The attention's sparse select is launched for every stream with the bucket as its context. Its kernels read each row's real end from the device, so the extra blocks and chunks score, select and merge nothing, and a replay computes the eager step's bits.
- Per replay, only the rows' positions are uploaded, one pinned copy of the step's integer table.
- A key is captured the second time it is seen, so a one-off set of chaining streams stays eager. At most 32 graphs; the least recently replayed goes first.
- Steps of more than one row a stream, and image streams, stay eager.

`TENSORFOLD_MTP_GRAPHS=0` runs every step eagerly.

The bits do not change: a replay computes what the eager step computes, so the drafts, and therefore which drafts land, are the same. The replies are verified as before.

Measured on one DGX Spark through the server, interleaved A/B, 3 passes an arm, arm order rotated, cold n-gram table every boot, median tok/s a request:

| Workload | 1 stream | 2 streams | 4 streams |
| --- | ---: | ---: | ---: |
| code, before | 90.2 | 63.6 | 42.1 |
| code, after | 91.3 (+1.2%) | 64.5 (+1.4%) | 42.4 (+0.7%) |
| prose, before | 74.6 | 51.0 | 32.2 |
| prose, after | 75.2 (+0.8%) | 51.5 (+1.0%) | 32.3 (+0.3%) |

Prefill was unchanged (8k / 32k / 128k: 2,548 / 2,634 / 2,301 -> 2,543 / 2,638 / 2,298 tok/s). ## 23. `qwen-pr-ple-defer`

**Title:** Patch 0017: a decode round's n-gram rows read while the GPU runs layers 0-1: with 0016, decode +1.8 to +2.2%, same bytes

**Body:**

## Description and Motivation

A decode round's `stage()` looks up every n-gram layer's rows, reads them (from SSD with `PLE_ON_SSD=1`) and copies them to the GPU before the forward starts. The GPU waits for all of it, although the first n-gram layer only comes after layers 0 and 1.

This patch adds `stage(..., defer_ple=True)`. The token ids still go up in `stage`, but the n-gram rows are looked up, read and copied when the forward reaches its first n-gram layer: `ple_block` runs the staging (`b.ple_staging`) before its first kernel, then records the stream's event. So the host reads the rows while the GPU runs the layers before it. The same bytes land in the same buffers ahead of the same kernels on the stream; nothing else changes.

A decode round alone defers. A round that shares its forward with a prompt pass stages the rows first, as before. `TENSORFOLD_PLE_DEFER=0` always stages them first.

The bits do not change, for the reason above.

## 24. `qwen-pr-tokenize-nogil`

**Title:** Patch 0018: no stall at a long request's start: the server tokenizes with Python's GIL released

**Body:**

## Description and Motivation

The server turns each prompt into ids with the tokenizer's `encode` (`App._prepare` for chat and completions, `App.decisions`, the forced think close and the tool-call gate). HF tokenizers' `encode` holds Python's GIL for the whole text: ~0.36 s at 256k tokens on the DGX Spark. The engine loop that schedules every stream's rounds runs in the same process, so while a long prompt is being tokenized, every other stream stops.

This patch routes every one of those calls through one helper, `App._encode_ids(text, special)`, which calls `self.tok.encode_batch_fast([text], add_special_tokens=special)[0].ids`: the same ids, computed with the GIL released, and faster because it skips the character offsets nothing in the server reads.

The ids do not change, so neither do the replies.

`0018` is a placeholder. This PR does not depend on my other PRs, and none of them depends on it.
