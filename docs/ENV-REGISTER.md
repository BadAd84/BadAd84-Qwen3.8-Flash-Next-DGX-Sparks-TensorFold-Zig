# The env register: every setting the serve reads is set in our env

`scripts/qwen38/zig/target/env/register.env` exists because a newer base can carry a default-on
decision that appears in no env file, and leaving it unset silently inherits its cost. It happened:
upstream added `shared_stop = 0.6` on 2026-11-10, which limits greedy drafting beside another open
stream. Production's engine predates it, so production drafted 3.03 tokens a round while ours drafted
1.92, and the difference read as an engine gap. Turning the gate off is worth 7 to 11 percent at two
to eight streams and closed 54 percent of the prose gap (`work/ProseDraft/RESULT.md`). Neither
`dev.env` nor `prod.env` named the setting, so no name-level sweep could find it.

## The rule: presence is the gate, and every value is stated

The owner's rule (2026-11-23): **no setting may be unset**. Every setting the served engine reads is
written in `scripts/qwen38/zig/target/env/dev.env` at a stated value. Choosing the engine default is a
decision like any other, and it is written down as the engine's own default, taken from the read site
that supplies it and cited there. The register no longer judges names, it forces values: a setting with
no line in `dev.env` fails the gate whether or not anyone wrote a note about it.

`check-env-coverage.py` therefore fails on:

| failure | meaning |
|---|---|
| `MISSING` | the served table has the setting and `dev.env` has no line for it |
| `VERDICT-ONLY` | the register carries a note for it and `dev.env` still does not set it |
| `WORKLIST` | a temporary `# missing NAME=` line is still in the register |
| `STALE` | the register annotates a setting the served table does not have |

The four old verdicts survive as **annotations on values that are already set**, never as substitutes
for setting them: `default-ok` (we keep the engine default, and the line says which read site gives
it), `debt` (set, but the choice is unmeasured and counted), `unreachable` (set, but the path cannot
run on this serve, with the reason). A note without a value is the `VERDICT-ONLY` failure.

The register is generated by `update-env-register.py` at a re-seat, which appends a temporary
`# missing NAME=<default>` line for each setting the table has gained. The worklist is work in
progress, never a resting state: each line is moved into `dev.env` with its citation and deleted from
the register. **A rebase that adds a setting fails the gate until its value is written**, which is the
point: a new upstream knob cannot inherit a default in silence.

Two settings have a default that no value can express, because their reader tests whether the variable
is *present* rather than parsing its text:

| setting | why absence is the value |
|---|---|
| `TENSORFOLD_CUDA_KERNELS` | `zig/src/cuda/aot.zig:15-23` loads the installed `share/tensorfold/cuda/sm<cap>` set when the variable is unset and the engine's own kernels otherwise; `native` forces the built-ins, and a blank value is refused as a folder name (`docs/environment.md:119`). |
| `TF_ROCE_GID_INDEX` | `zig/src/cuda/roce.zig:255` searches the GID table for a RoCE v2 IPv4 entry only when the variable is unset; any text, blank included, is parsed as an index (`zig/src/cuda/roce_verbs.zig:146-160`). |

Those two are written as `export NAME` with no value, which `dev.env` sources into a process where the
variable stays unset (verified: `env -i bash` sourced the file, both names absent from the environment,
every other export present). The line and its citation are the record that the absence was chosen; the
gate counts the statement as carried.

## The explicit defaults section

`dev.env` keeps two sections. The top is measured levers, each with the receipt that measured it. The
bottom, headed `explicit defaults`, holds the engine's own default for every setting that has no
measured gain: one `export NAME=value` each, preceded by the read site that gives the default and the
evidence path. A value that differs from the engine default is not allowed in that section; it belongs
in the measured section with its cells.

`check-dev-env.py` requires a `work/`, `docs/` or `scripts/` citation within eight lines above every
export, so a default line carries the same evidence obligation as a measured one.

## At every re-seat

1. `python scripts/qwen38/zig/target/env/update-env-register.py --table <new tree>/zig/src/platform/environment.zig \
  --dev scripts/qwen38/zig/target/env/dev.env --register scripts/qwen38/zig/target/env/register.env \
  --scopes flashnext,cuda,common --defaults-from-tree <new tree>/zig`
   appends a `# missing NAME=<literal>` line, with its read site, for every setting the table now has
   that `dev.env` does not set and the register does not already annotate.
2. `python scripts/qwen38/zig/target/env/check-env-coverage.py --table <tree>/zig/src/platform/environment.zig \
  --dev scripts/qwen38/zig/target/env/dev.env --register scripts/qwen38/zig/target/env/register.env --scopes flashnext,cuda,common`
   fails while any worklist line remains. Run it from the tree we actually serve; `--strict-carried`
   also fails a `dev.env` export that tree does not read (a retired or misspelled name).
3. Resolve every worklist line from the new tree's own source, never by guessing: read the expression
   at the cited read site, follow it to a literal (a constant, a struct field initialiser, a function's
   default parameter), write that literal in the `explicit defaults` section with its citation, and
   delete the line from the register. A name the new tree does not read at all is a stale entry: delete
   it and say so, do not invent a value.
4. `python scripts/qwen38/zig/target/env/check-dev-env.py` and the coverage gate, both green, with the
   final lines quoted in the change that lands them.

The 78 are the `flashnext`, `cuda` and `common` rows of `zig/src/platform/environment.zig`: 8 measured
levers at the top of `dev.env` and 70 stated defaults below them, two of the 70 as the presence
statements above. The six exports that this serve's table does not have are the series' own settings
and production-engine-only names; each is checked for a reader when the gate runs with
`--strict-carried` against the served tree.

The parser reads each row field by field rather than by one fixed pattern. The first version matched the
whole row shape and therefore saw 31 of 82 `dsv41` rows and 65 of 261 rows at main: any row carrying an
optional field such as `trim` or `no_word` was invisible, which is the same blind-instrument failure the
register exists to prevent. It was caught when the same scripts were run against another serve's table and
the totals disagreed with a plain grep.

The scripts are portable: `--table`, `--dev`, `--register`, `--scopes` and `--carried-pattern` are all
arguments, so another serve repo runs the same files against its own family scope and launcher env (the
DeepSeek-V4.1 repo carries a copy and the write-up in its `docs/ENV-REGISTER.md`).
