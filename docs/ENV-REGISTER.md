# The env register: every setting the served tree reads is set in our env

`scripts/qwen38/zig/target/env/register.env` exists because a newer base can carry a default-on
decision that appears in no env file, and leaving it unset silently inherits its cost. It happened:
upstream added `shared_stop = 0.6` on 2026-11-10, which limits greedy drafting beside another open
stream. Production's engine predates it, so production drafted 3.03 tokens a round while ours drafted
1.92, and the difference read as an engine gap. Turning the gate off is worth 7 to 11 percent at two
to eight streams and closed 54 percent of the four-stream prose gap (`docs/receipts/ProseDraft/RESULT.md`). Neither
`dev.env` nor `prod.env` named the setting, so no name-level sweep could find it.

## The rule: presence is the gate, and every value is stated

The owner's rule (2026-11-23): **no setting may be unset**. Every setting the served engine reads is
written in `scripts/qwen38/zig/target/env/dev.env` at a stated value. Choosing the engine default is a
decision like any other, and it is written down as the engine's own default, taken from the read site
that supplies it and cited there. The register does not judge names, it forces values: a setting with
no line in `dev.env` fails the gate whether or not anyone wrote a note about it.

`check-env-coverage.py` therefore fails on:

| failure | meaning |
|---|---|
| `MISSING` | the served table has the setting and `dev.env` has no line for it |
| `VERDICT-ONLY` | the register carries a note for it and `dev.env` still does not set it |
| `WORKLIST` | a temporary `# missing NAME=` line is still in the register |
| `STALE` | the register annotates a setting the served table does not have |
| `NO-VALUE` | a bare `export NAME` with no value, which says nothing about the container |
| `IMAGE-BAKED` | `unset NAME` for a name the served image's own ENV carries |
| `DUPLICATE` | the env states one setting twice, so the last line silently wins |
| `PASSAGE-LOST` | a measured value whose name the recipe launcher's filter cannot pass into the container |

The four old verdicts survive as **annotations on values that are already set**, never as substitutes
for setting them: `default-ok` (we keep the engine default, and the line says which read site gives
it), `debt` (set, but the choice is unmeasured and counted), `unreachable` (set, but the path cannot
run on this serve, with the reason). A note without a value is the `VERDICT-ONLY` failure.

The register is generated by `update-env-register.py` at a re-seat, which appends a temporary
`# missing NAME=<default>` line for each setting the table has gained, and `# missing NAME=presence`
where the reader's default is `null` (a presence test). The worklist is work in progress, never a
resting state: each line is moved into `dev.env` with its citation and deleted from the register. **A
rebase that adds a setting fails the gate until its value is written**, which is the point: a new
upstream knob cannot inherit a default in silence.

## How the env reaches the container, read from the recipe's own launcher

The passage is one loop in the recipe's `start.sh` (spark6 `~/qwen-zig/start.sh`, the served launcher):

```bash
ENV_ARGS=(-e HF_HUB_OFFLINE="${HF_HUB_OFFLINE:-1}")
while IFS='=' read -r name _; do
  [[ "$name" == TENSORFOLD_API_KEY ]] && continue
  ENV_ARGS+=(-e "$name=${!name}")
done < <(env | grep -E '^(TENSORFOLD|TF_)[A-Z0-9_]+=' || true)
...
here_cmd=(docker run -d --name "$CONTAINER_NAME" ... "${ENV_ARGS[@]}" "${KEY_ARGS[@]}" ... "$IMAGE" ...)
```

Three consequences, and they are the whole presence rule:

- **Only names present in the launcher's process environment are passed**, each as `-e NAME=value`, and only
  those two prefixes (the secret `TENSORFOLD_API_KEY` is passed as a bare `-e NAME`, so it never appears in
  the argv we log). Every `dev.env` name is `TF_*` or `TENSORFOLD_*`, so every one is in reach.
- **`unset NAME` therefore reaches the container as absence**: the name is not in `env`, no `-e` is
  generated, and the container keeps only whatever the image's `ENV` supplies. That is why the absence
  form is real and why the dump check (arm A's 30 names) settles `TF_ROCE_GID_INDEX`.
- **`export NAME` with no value generates no `-e` at all**: the shell does not export a name it never set,
  so the image's `ENV` value passes through untouched. That is the exact chain EnvBoot's boot hit, and it
  is why the bare form is a failure now rather than a statement.
- **The filter also decides which of our settings can act.** The recipe's launcher passes only
  `TENSORFOLD_*` and `TF_FLASHNEXT_*`. `dev.env` states 27 `TF_*` names (26 with a value, `TF_ROCE_GID_INDEX` as
  `unset`), and those never reach the engine through this launcher. All 26 are in the `explicit
  defaults` section, so each is the value the engine already uses: inert, and harmless. The gate makes
  the distinction mechanical: `--passes` takes the launcher's filter, and a value above the defaults
  marker that the filter cannot carry is `PASSAGE-LOST`, because a measured lever that cannot act is a
  defect; one below it is reported as an advisory. The gate also fails a setting stated twice
  (`DUPLICATE`), since the last line silently wins.

## Presence-tested settings: `unset`, or a value, never a bare `export`

Two rows have a default that no value can express, because their reader tests whether the variable is
*present* rather than parsing its text:

| setting | why absence is the value |
|---|---|
| `TENSORFOLD_CUDA_KERNELS` | `zig/src/cuda/aot.zig:15-22` loads the installed `share/tensorfold/cuda/sm<cap>` set when the variable is unset, and `native` forces the engine's own kernels; any other text is a folder and a blank one is refused (`docs/environment.md:116`). |
| `TF_ROCE_GID_INDEX` | `zig/src/cuda/roce.zig` searches the GID table for a RoCE v2 IPv4 entry only when the variable is unset; any text, blank included, is parsed as an index (`zig/src/cuda/roce_verbs.zig:146-160`). |

A presence-tested setting has exactly two honest forms, and `export NAME` with no value is neither:

1. **`unset NAME`** is real absence. `dev.env` is sourced into the launcher's process (`set -a; .
   dev.env`, the knob screen's own boot), so the name is gone from what the launcher and the recipe
   read, and it also clears a value the parent shell had: measured, a valueless `export` left an
   inherited `TF_ROCE_GID_INDEX=3` in place while `unset` removed it (`docs/receipts/EnvServed/absence-probe.txt`).
   It is honest only where nothing else supplies the name. That is `TF_ROCE_GID_INDEX`: arm A's
   container env, the r5 FP4 image through the dev launcher, carries 30 serve names and not this one
   (`docs/receipts/QRerun/box/out/QA/env.txt`). If an image or a launcher ever supplies it, the register records
   that with `# image-baked` and the setting is stated with a value.
2. **`export NAME=<value>`** where the image bakes the name. The loop passes `-e NAME=value`, and `-e`
   wins over the image's `ENV`; a name the launcher never exports generates no `-e` at all, so the
   image's value stands, and nothing in the shell can remove an image's `ENV` from the container. An
   empty value is also a value (it is passed as `-e NAME=`, and for this row a blank is a folder name
   that is refused), so the only honest statement is the value that realises the intended default. The
   register records the bake as `# image-baked NAME=<value>: <evidence>`, which fails if the name is
   written `unset`.

**Why the old bare `export NAME` was wrong.** It marked the name for export in the sourcing shell and
set nothing; EnvBoot's dev boot measured the consequence and is the probe for this decision. `dev.env`
stated `TENSORFOLD_CUDA_KERNELS` with no value, the r5 image's ENV supplied
`/opt/tensorfold/share/tensorfold/cuda/sm121`, the container therefore ran on a captured kernel set,
and the engine refused the documented fp8 shape before loading weights:

```
tensorfold: --kv-cache fp8 runs on Flash Next's own glue on one rank: serve it without --tp, --slide or
  TENSORFOLD_CUDA_KERNELS, or without --kv-cache fp8
```

(`docs/receipts/EnvBoot/RESULT.md` section 2b.) The line read as "default" while the boot ran on a baked value,
which is exactly the silent inheritance the register exists to prevent. The other half of the probe is
the receipts' own container environments: a boot that passes `native` carries
`TENSORFOLD_CUDA_KERNELS=native` in `docker inspect` (`docs/knob-receipt-2026-11-20/receipt/w1/boot.md`,
first line of `docs/receipts/KvTierDedup/ev/out/new/seed/env.txt`), so an explicit value reaches the container
and overrides the image's.

`dev.env` therefore states `TENSORFOLD_CUDA_KERNELS=native` (in the enabler block beside the page
pool, with the refusals it clears) and `unset TF_ROCE_GID_INDEX`.

Current state, 2026-11-23:

- **Both r5 images bake the variable**: `tensorfold-qwen38:qr-a-r5-1ece6e6db` and
  `tensorfold-qwen38:qr-b-r5int4-1ece6e6d` carry

  that captured Triton set (`docs/KNOB-SCREEN.md`; the EnvBoot boot above observed it in force).
- **The shape they forbid**: a captured set is refused with `--kv-cache fp8` and with the page pool on

  `error.FlashNextPagesUnsupported` whenever `captured` is not null). The documented dev shape is fp8
  with `TF_FLASHNEXT_KV_PAGES=4096` at 8 streams and 262,144 tokens, so it cannot boot on these images
  while the variable is absent: the container runs on the captured set.
- **What fixes it**: `native` clears `captured` (`zig/src/cuda/aot.zig:17`) and both are admitted at
  TP=1. `dev.env` now states it, so the refusal is gone by construction. The shape's memory plan is
  the one the tier window measured at exactly this shape: the first stream's caches in the model's
  4.99 GiB, seven more taking 278 pages of 4,096 rows (20.02 GiB) inside the 31.0 GiB the budget
  leaves after the 10 GiB reserve (`docs/receipts/KvTierShip/RESULT.md` section 1, the `levels/off` control,
  whose plan line ends `own glue kernels`, that is `native`).
- **What differed in the tier windows**, which booted this shape for 30 cells: nothing about their
  images. Every cell's container env carried `TENSORFOLD_CUDA_KERNELS=native`, passed explicitly, so
  they were never on a captured set (`docs/receipts/KvTierDedup/ev/out/new/seed/env.txt` line 1). The shape
  needs no image without the baked variable and no engine change; it needs the setting stated.
- **The cost of `native`**: the installed captured set is never loaded, so whatever speed it could give
  is unmeasured on this stack (A3 in `docs/KNOB-COVERAGE.md`). It is stated as `debt` in the register.

## The explicit defaults section

`dev.env` keeps two sections. The top is measured levers and enablers, each with the receipt that
measured it. The bottom, headed `explicit defaults`, holds the engine's own default for every setting
that has no measured gain: one `export NAME=value` each, preceded by the read site that gives the
default and the evidence path. A value that differs from the engine default is not allowed in that
section; it belongs in the measured section with its cells.

`check-dev-env.py` requires a `work/`, `docs/` or `scripts/` citation within eight lines above every
statement (`export NAME=value` or `unset NAME`), so a default line carries the same evidence obligation
as a measured one.

## Stated is delivered

The launcher forwards `^(TENSORFOLD|TF_)[A-Z0-9_]+=`, so every setting the engine's table declares is reachable,
including the 26 bare `TF_` names the old filter dropped. Two proofs stand behind the change, both measured.

- **It is behaviour-neutral.** Of the 27 statements the old filter dropped, 11 equal what absence yields and 16 are
  inert because their only readers are in `families/qwen3_5/`; 0 differ, so a widened filter delivers defaults only
  (`docs/receipts/EnvForward/TABLE.md`).
- **It delivers on a boot.** On the same image, dev env and shape as the reference boot, a widened launcher carried
  all 26 names at their stated values, kept all 74 previously forwardable names equal, kept both `unset` lines
  absent, read `1176 of 1176` on the window self-check, and returned the same three fixed-prompt replies (carried
  100 equal, 0 differ, 0 absent; beyond-dev-env 48; levers 8/8; hashes 3/3). Production was restored pinned and its
  drift check read EQUAL (`docs/receipts/LauncherAB/SUMMARY.txt`, with its 26-name and env-proof logs beside it).

The change is deployed to all four launchers: the recipe's `start.sh`, its two nsys copies, and `~/qwen-zig/start.sh`.
With the delivered filter the coverage gate reads `coverage: 95 settings in scope, set 95, missing 0, absent 2,
annotations 2, worklist markers 0, passage-lost 0`, rc 0. The upstream form is packaged at
`upstream/recipe-launcher-tf-env/` as a local record. The recipe repository is not a contribution target (owner,
2026-11-23), so no pull request is opened there.

## The production copy cannot drift

`prod.env` is a hand copy of the production launcher's environment, taken from `docker inspect` of
`qwen38-flash-next-tf`, and a hand copy drifts: the 2026-11-20 capture carried 52 settings and the 2026-11-23
one 54 (`TENSORFOLD_CUDA_KERNELS` and `TENSORFOLD_VISION_PYTHONPATH` were the two added), with nothing
comparing either copy to the container. `scripts/qwen38/zig/target/env/check-prod-env.py` closes that:

The check refuses to compare unless the container it reads is on the pinned production image (`rc 3`): every
GPU window serves under the same container name, so a run during a window would otherwise report the window's
environment as production drift. Observed 2026-11-23: a run during a dev window read that window's 122-name dev
environment against production's 54 and looked like 69 problems.

```
python scripts/qwen38/zig/target/env/check-prod-env.py
prod-env: 54 settings in prod.env (54 stated, 0 unset), 54 in the container, 54 equal, 0 problem(s)
```

It reads the container's own `Config.Env` (`docker inspect qwen38-flash-next-tf --format
'{{json .Config.Env}}'`, or a saved copy through `--inspect`), compares every `TF_*`/`TENSORFOLD_*` name in
both directions, and fails on a changed value, a name the copy states and the container lacks, a name the
container carries and the copy lacks, a duplicate line, and a bare `export`; `unset NAME` asserts absence.
`TENSORFOLD_API_KEY` is never compared. The dry run plants one changed value, one missing name and one extra
name and gets three findings (`DIFF`, `MISSING`, `EXTRA`, rc 1), while a copy generated from `prod.env`
itself reads 54 equal (rc 0).

## At every re-seat

1. Locate the served tree first: read the image's `tf.tree.manifest` label and find the tree in
   `work/` whose manifest hashes to it. Do not run the gate against a newer tree by habit.
2. `python scripts/qwen38/zig/target/env/update-env-register.py --table <served tree>/zig/src/platform/environment.zig \
  --dev scripts/qwen38/zig/target/env/dev.env --register scripts/qwen38/zig/target/env/register.env \
  --scopes flashnext,cuda,common --defaults-from-tree <served tree>/zig`
   appends a `# missing NAME=<literal>` line, with its read site, for every setting the table now has
   that `dev.env` does not set and the register does not already annotate; a presence test with a
   `null` default is appended as `# missing NAME=presence`.
3. `python scripts/qwen38/zig/target/env/check-env-coverage.py --table <served tree>/zig/src/platform/environment.zig \
  --dev scripts/qwen38/zig/target/env/dev.env --register scripts/qwen38/zig/target/env/register.env \
  --scopes flashnext,cuda,common --passes '^(TENSORFOLD|TF_)'`
   fails while any worklist line remains or a measured value cannot reach the container. `--strict-carried` also fails a `dev.env` export that tree
   does not read, so it is for a serve whose env carries nothing else; here it would name the seven
   classified names above, and it is not part of the standing command.
4. Resolve every worklist line from the new tree's own source, never by guessing: read the expression
   at the cited read site, follow it to a literal (a constant, a struct field initialiser, a function's
   default parameter), write that literal in the `explicit defaults` section with its citation, and
   delete the line from the register. A name the new tree does not read at all is a stale entry: delete
   it and say so, do not invent a value. A presence test takes `unset NAME` or, where the image bakes
   the name, the value that realises the default.
5. `python scripts/qwen38/zig/target/env/check-dev-env.py` and the coverage gate, both green, with the
   final lines quoted in the change that lands them.
6. Run `python scripts/qwen38/zig/target/env/check-prod-env.py` in every window's restore step, after
   production is back: it fails on any difference between `prod.env` and the live container, so a restore
   that leaves a stale copy cannot pass as done. The box must be up and the container named
   `qwen38-flash-next-tf`, or pass `--container`; `--inspect` takes a saved `docker inspect` when the gate
   runs off the box.

The parser reads each row field by field rather than by one fixed pattern. The first version matched the
whole row shape and therefore saw 31 of 82 `dsv41` rows and 65 of 261 rows at main: any row carrying an
optional field such as `trim` or `no_word` was invisible, which is the same blind-instrument failure the
register exists to prevent. It was caught when the same scripts were run against another serve's table
and the totals disagreed with a plain grep.

The scripts are portable: `--table`, `--dev`, `--register`, `--scopes`, `--carried-pattern`,
`--absent-pattern`, `--no-value-pattern`, `--passes`, `--measured-before` and `--defaults-from-tree` are
all arguments, so another serve
repo runs the same files against its own family scope and launcher env (the DeepSeek-V4.1 repo carries a
copy and the write-up in its `docs/ENV-REGISTER.md`).
