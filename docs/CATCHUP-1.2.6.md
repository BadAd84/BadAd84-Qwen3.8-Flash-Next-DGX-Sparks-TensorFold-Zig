# Catching up with the production stack on TensorFold v1.2.6

Measured on spark6 on 2026-11-11, one fresh boot a cell, the target's own settings (nvfp4 checkpoint, fp8 KV,
262,144-token windows, every slot busy, 512-token requests, three passes, median).

## The gap, measured

| arm | 1 stream prose / code | 2 | 4 | 6 |
|---|---|---|---|---|
| target document (production, older stack) | 70.9 / 113.0 | 103.3 / 173.7 | 162.3 / 254.0 | 202.2 / 311.8 |
| production image on this box today | 70.4 / 112.1 | 104.3 / 173.7 | 165.1 / 254.8 | 204.9 / 312.3 |
| v1.2.6 with all 30 patches, defaults | 54.6 / 78.6 | 69.8 / 115.7 | 108.6 / 164.8 | will not boot |
| the same stack with production's whole env | 51.9 / 79.1 | - | 109.6 / 165.4 | - |

So: production reproduces the target document within 1.7% at every level, which validates the harness and the
box; our stack is 23-35% behind; and production's forty tuned knobs change nothing on our stack, so the gap is
code, not configuration. At 6 streams and 262,144 tokens our stack also refuses to boot on its per-stream
memory estimate.

For scale, on the earlier sweep at bf16 and 131,072 tokens our stack measured 49.3 / 82.3 at one stream against
stock v1.2.6's 50.3 / 71.2, i.e. the levers we did port are worth about 15% on code decode, while production
sits 57% above stock. The missing 40 points are levers production has that our tree does not.

## Why: production is a different engine, with ~93 knobs ours does not have

Production runs the ai-engine tree at `e5139fc` (image label `ai-engine.src-sha256`). Our fork's `main` is that
stack (`27b6700c`); our v1.2.6 tree is upstream `6e9af930` plus the 30 patches. Comparing the two:

- knobs: 101 in production, 71 in ours, 93 unique to production;
- structure: production's Flash Next is 109 files with large modules (`cuda_engine.zig`, `cuda_forward.zig`,
  `cuda_native.zig`, `cuda_int4.zig`, `cuda_mtp_q4.zig`, `cuda_fp8.zig`, `cuda_ngram.zig`); v1.2.6 is 585 files
  with per-kernel units.

So this is not a cherry-pick: each production lever has to be re-implemented against v1.2.6's structure. The
lever map below is the port backlog, generated by mapping every production-only knob to the code it gates.

The decode-critical clusters, in the order they should be attempted:

1. **Draft and MTP**: `TF_FLASHNEXT_DRAFT_INT4`, `TF_FLASHNEXT_MTP_FP8`, `TF_FLASHNEXT_MTP_Q4` (and `_MSE`),
   `TF_FLASHNEXT_DRAFT_DEPTH_SHARED`, `TF_FLASHNEXT_DRAFT_CONTINUE`, `TF_FLASHNEXT_DRAFT_PROPOSE`,
   `TF_FLASHNEXT_HEAD_ROW_TILES`, `TF_FLASHNEXT_INT4_TILE`, `TF_FLASHNEXT_INT4_PROMPT_DOWN`,
   `TF_FLASHNEXT_INT4_PROMPT_GATE_UP`. This is where most of production's decode headroom plausibly lives: a
   4-bit/FP8 drafter proposes more tokens per round than our bf16 draft head.
2. **Round scheduling**: `TF_FLASHNEXT_DEPTH`, `TF_FLASHNEXT_BATCH_DRAWS`, `TF_FLASHNEXT_BATCH_WINDOWS`,
   `TF_FLASHNEXT_EARLY_DRAW`, `TF_FLASHNEXT_DRAW_ONCE`, `TF_FLASHNEXT_FILL`, `TF_FLASHNEXT_FILL_LAYERS`,
   `TF_FLASHNEXT_DROP_PAGES`, `TF_FLASHNEXT_COST_RETIME`.
3. **FP8 kernel variants**: `TF_FLASHNEXT_FP8_LD`, `TF_FLASHNEXT_FP8_FUSED_SPLIT`,
   `TF_FLASHNEXT_FP8_FUSED_SPLIT_N`, `TF_FLASHNEXT_FP8_PROMPT_TILES`, `TF_FLASHNEXT_GLUE_FUSE`,
   `TF_FLASHNEXT_GLUE_SPLIT`, `TF_FLASHNEXT_ATTN_MULTI`, `TF_FLASHNEXT_QSA_SELECT`, `TF_FLASHNEXT_QSA_TILE`,
   `TF_FLASHNEXT_UPMIX_DECODE`, `TF_FLASHNEXT_REDUCE_ACT`.
4. **Copy window**: `TF_FLASHNEXT_COPY_MISS`, `_RAMP`, `_RESYNC`, `_RESYNC_PROMPT_ONLY`, `_SHARED`,
   `TF_FLASHNEXT_WINDOW`, `TF_FLASHNEXT_PRODUCT_STREAMS`, `TF_FLASHNEXT_SEQ_POOL`, `TF_FLASHNEXT_WARM_POOL`,
   `TF_FLASHNEXT_SOLO_MAX`. We have a copy window but nothing like production's gating of it.
5. **MoE and prompt**: `TF_FLASHNEXT_EXPERT_SHAPE`, `TF_FLASHNEXT_EXPERT_SMS_FREE`, `TF_FLASHNEXT_COUNT_EXPERTS`,
   `TF_FLASHNEXT_INT4AR_FAST`, `TF_FLASHNEXT_FP4_SERIAL`, `TF_FLASHNEXT_L2PF`, `_L2PF_BYTES`,
   `TF_FLASHNEXT_MEDIA_GRAPHS`, `TF_FLASHNEXT_COMM_PRIORITY`.
6. **N-gram**: production's `cuda_ngram.zig` / `cuda_ngram_host.zig` sit behind the same three knobs we have,
   but the implementation differs; treat it as already ported until a measurement says otherwise.

## What this means for the plan

The self-check defect (windows falling back from 48 to 32 rows, `0 of 2080`) is real, is confined to patches
0016-0030, and costs some decode, but it cannot explain 23-35%: production serves a 64-row window and our whole
rows lever is worth about 3-6% at one to two streams. The bulk of the catch-up is clusters 1 and 2 above, and
the only honest order is: fix the rows regression (it gates the copy lever), then port the drafter and round
scheduling levers, measuring each against this table.

## Where the time actually goes: the round, not the tokens a round yields

Attribution on the production tree, with production's own launcher (its binary predates `--kv-cache`, so the 1.2.6
recipe cannot boot it at all: every earlier production cell was silently measuring the already-running container).
One stream, one pass, 512 tokens, same prompts:

| arm | prose tok/s | code tok/s | prose rounds | code rounds |
|---|---|---|---|---|
| production, all levers on | 71.5 | 127.7 | 186 | 81 |
| `MTP_Q4=0` | 75.0 | 130.6 | 186 | 81 |
| `DRAFT_INT4=0` | 72.4 | 126.4 | 186 | 81 |
| `UPMIX_DECODE=0` | 75.1 | 130.5 | 186 | 81 |
| `QSA_SELECT=0` | 75.0 | 130.7 | 186 | 81 |
| `EARLY_DRAW=0` | 75.3 | 130.9 | 186 | 81 |

Every arm came out 3-5% faster than the base, including knobs that cannot plausibly help, which is the cold-boot
confound of a first boot (the n-gram tables page from disk), so no single knob is the lever. The round counts are
identical across arms, which is the useful part: those knobs change the cost of a round, not how many tokens it
yields, and none of them carries a large share of the gap.

The round economics, same prompt, one stream:

| | ms a round, prose | ms a round, code | rounds for 512 tokens, code |
|---|---|---|---|
| production | 38.5 | 49.5 | 81 |
| our v1.2.6 stack | 64.7 | 77.7 | 90 |

So production's verify round costs about 1.6x less than ours, and it needs about 10% fewer rounds. The gap is
per-round cost, which is the engine: production's `cuda_engine` / `cuda_forward` / `cuda_fp8` architecture plus the
FP8 MTP drafter overlay (`TF_FLASHNEXT_MTP_FP8` points at a separate azampatti INT4-AutoRound-derived drafter weight
set that our tree does not load at all). That is what has to be ported, and it is where the levers of cluster 1 and 2
land.

## The 262,144-target memory refusal

Our stack refuses 6 streams at 262,144 tokens: "`--parallel 6 needs 30.23 GiB for its streams at a 262144-token
window, and the CUDA memory budget leaves 27.27 GiB`", i.e. 5.04 GiB a stream. Production serves 8 streams in
25.61 GiB, 3.20 GiB a stream. Measured:

- switching drafting off (`TF_FLASHNEXT_DRAFTS=0`) leaves the estimate at 30.23 GiB, unchanged: the budget is
  computed from the loaded draft head (`cuda_lanes_load.streamBytes` adds `mtp.Draft.bytes(window, head_ids, ...)`
  whenever a head is present), so the drafts flag does not enter it;
- the sequence alone, from `cuda_seq_bytes.seqBytesFor` at fp8 and 262,144 tokens, is about 3.21 GiB a stream:
  36 DeltaNet layers of conv tails and fp32 states (0.11 GiB), 12 attention layers at 1,056 bytes a position a
  layer (3.09 GiB), pooled indexer blocks (0.02 GiB).

So of the 5.04 GiB priced a stream, about 3.21 is the sequence and roughly 1.8 is the draft head's caches plus the
draft pass's own arrays (`cuda_mtp_draft.zig`'s `bytes`: two bf16 head caches at the full window, the indexer keys,
the pooled blocks, the logits, the saved states and the per-layer state). Production does not pay that at bf16: its
drafter runs the FP8 MTP overlay. Half of 1.8 GiB takes a stream to about 4.1 GiB, and 6 streams to 24.8 GiB, which
fits the 27.27 GiB budget.

Two fixes follow, in expected value order: price and serve the draft head caches in fp8 (the port of production's
`TF_FLASHNEXT_MTP_FP8`, cluster 1), or size them to the window the serve actually accepts rather than the full
context. Neither is done yet, and the split between "draft caches" and "draft arrays" above is arithmetic from the
sizing functions, not an instrumented measurement: the next step is one boot that prints `streamBytes`' parts.

## The FP8 drafter port, scoped against what v1.2.6 already has

Production's drafter lever is `TF_FLASHNEXT_MTP_FP8`, an overlay directory of the MTP layer's linears on block FP8
(`tools/mtp_fp8.py` builds it). Its patch upstream is 50 lines across two files: an `overlay2` option on the weight
loader and one condition that makes the MTP layer's attention weights load through the block-FP8 path.

What v1.2.6 already carries: an FP8 experts loader (`cuda_fp8_experts_load.zig`) whose tests load the MTP layer's
experts by name (`language_model.mtp.layers.0.mlp`), and FP8 KV with 1,056 bytes a position a layer. What it does
not carry: any `int4ar` / overlay plumbing at all (28 files mention fp8; none of them has an overlay), and the MTP
layer's attention linears load as 4-bit affine like the rest of the body.

So the port is three commits, in this order:

1. **Price the draft head caches by their own format.** `cuda_mtp_draft.zig`'s `bytes` assumes bf16 head caches; with
   an fp8 head the same stream drops by roughly 0.9 GiB, which is what puts six streams at 262,144 inside the
   budget. This is memory only and does not touch kernels.
2. **Load the MTP layer's attention linears in FP8.** The experts half exists; this is the attention half, plus the
   overlay-directory plumbing if we want the weights in a separate directory rather than the checkpoint.
3. **Measure it as an artifact**: the same cells as the table at the top of this document, plus the round economics,
   because the whole point of the drafter lever is a cheaper round (production 49.5 ms a code round against our
   77.7 ms).

Nothing of this is done yet. The diagnostic phase of the catch-up is complete: the gap is measured, its mechanism is
the cost of a round, the levers that carry it are enumerated by knob and file, the memory refusal is explained, and
the rows regression is localised to patches 0016-0030 with the read-out, tile, chunk, HC and copy knobs excluded.

## Knob sweep on the new engine (step one: tune what already exists)

The new tree carries 68 `TF_FLASHNEXT_*` knobs that production's launcher never sets. Swept at the target's settings,
one fresh boot a cell, C=1 and C=4, one decode pass, with a discarded warm-up arm and a warm baseline (`base2`)
because a first boot is 1.4-2.0% cold on code and 5.5-6.0% on prose (the tables page from disk).

Against the warm baseline, every knob in the set is inert (within +/-0.3%) except three:

| knob | C1 code | C4 code | C1 prose | C4 prose | verdict |
|---|---|---|---|---|---|
| `WINDOW_GRAPH=0` | -29.0% | -0.6% | -30.6% | +1.7% | graph replay is worth about 40% at one stream and it is already ON |
| `WINDOW_ROWS=32` | +1.4% | -5.2% | +6.1% | +2.4% | a real 5% regression at four streams: never set it |
| `GATHER_READ=0` (for scale: the read-ahead lever) | +3.9% | +2.1% | +7.0% | +4.1% | see below |

`DECODE_GRAPH=1` with `SPLIT_DENSE=0`, `ATTN_LANES=1`, `CHUNK` 512 and 1024, `CHUNK_SOLO=1536`, `GREEDY_WIDE=8`,
`FACT_ROWS=128`, `READOUT_ROWS=128`, `PROMPT_GEMM2=0`, `PROMPT_HC2=1`, `HC_Q12=0`, `PREFILL_TAIL=0`,
`GATHER_THREADS=0`, and `TF_MTP_DRAFTS=0` all landed inside the noise.

Two consequences. First, the answer to "does an unused knob explain the 23-35%": no. The decode-path knobs the
production env never sets are either already on by default, or harmful (`WINDOW_ROWS`). Second, `TF_MTP_DRAFTS=0`
changing nothing means neither it nor `TF_FLASHNEXT_DRAFTS=0` is the drafting switch in this build, so the drafter's
contribution is still unmeasured and needs the real switch found before any drafter conclusion is drawn.

## Per-lever evaluation of our own patches (step two)

Each lever our patches gate is measured on/off at the target settings, C=1 and C=4, against a warm baseline
(`base2`), with a discarded warm-up arm; every arm's golden is compared against the baseline's. Results after the
A/B/A confirmation:

| head piece (0022) | `HEAD_PIECE=0` | see the batch table | | | | | |

The mechanism behind the read-ahead result is worth naming because it inverts the patch's premise: patch 0013 exists
to stop page faults on the checkpoint's 28.7 GiB n-gram mapping, and it reads rows with `pread` using `O_DIRECT`
where the file system allows. With the table's working set already resident, that path costs more than the faults it
avoids, so the plain reader (page faults through the mapping) wins. The obvious modify to test is the same row cache
with ordinary buffered reads instead of `O_DIRECT`, which would keep the parked readers and drop the alignment and
copy cost.

### The completed set, with the drafter and the stack

| batch | arm | C1 code | C4 code | C1 prose | C4 prose | golden | verdict |
|---|---|---|---|---|---|---|---|
| prompt path | `PROMPT_SHARED_DIRECT=0` | +0.0% | +0.2% | +0.2% | +0.4% | - | inert |

| prompt path | `HEAD_PIECE=0` | -0.3% | +0.1% | +0.2% | +0.1% | - | inert |
| drafter | `DRAFTS=0` (the recipe's switch: `--no-drafts`) | **-65.9%** | **-58.5%** | -56.2% | -40.1% | - | the drafter is worth 2.4x to 2.9x: protect it |
| 31 patches | `GATHER_DIRECT=0` (buffered row cache) | +2.9% | +1.9% | +6.3% | +3.8% | 6/6 identical | ties the plain reader |
| 31 patches | `GATHER_READ=0` (plain reader) | +2.8% | +2.1% | +6.8% | +3.9% | 6/6 identical | the simpler of the two equals |
| stacked | `GATHER_READ=0 ATTN_LANES=1 DECODE_GRAPH=1 SPLIT_DENSE=0 CHUNK=1024`, first pass | +3.1% | +3.1% | +6.5% | +5.3% | 6/6 identical | **the best measured set** |
| stacked | the same, second pass (ABBA) | +3.1% | +3.0% | +7.0% | +4.9% | 6/6 identical | confirmed |

Two conclusions. The micro-gains do stack: individually 0 to 2% each, together 3.1% at both stream counts on code and
5 to 7% on prose, reproduced twice against its own baseline. And the read-ahead path is now fully characterised: with
`O_DIRECT` it loses 2 to 7%, with the page cache it merely ties the plain reader, so the plain reader is the default
and patch 0031's knob stays as the opt-in for a box where the table is cold.

The measured set is recorded in `scripts/qwen38/zig/target/serve-env126.sh` (a launch through the recipe is
`env $(serve-env126.sh) IMAGE=... ./start.sh restart`), and `TF_FLASHNEXT_WINDOW_ROWS=32` is called out there as a
5% regression at four streams.
