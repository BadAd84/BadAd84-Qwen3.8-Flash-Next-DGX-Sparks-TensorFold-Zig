# Catching up with the production stack on TensorFold v1.2.6

Measured on spark6 on 2026-11-11, one fresh boot a cell, the target's own settings (nvfp4 checkpoint, fp8 KV,
262,144-token windows, every slot busy, 512-token requests, three passes, median).

## The gap, measured

| arm | 1 stream prose / code | 2 | 4 | 6 |
|---|---|---|---|---|
| target document (production, older stack) | 70.9 / 113.0 | 103.3 / 173.7 | 162.3 / 254.0 | 202.2 / 311.8 |
| production image on this box today | 70.4 / 112.1 | 104.3 / 173.7 | 165.1 / 254.8 | 204.9 / 312.3 |
| v1.2.6 with all 30 patches, defaults | 54.6 / 78.6 | 69.8 / 115.7 | 108.6 / 164.8 | will not boot |
| the same stack with production's whole env | 51.9 / 79.1 | - | 109.6 / 165.4 | - |

So: production reproduces the target document within 1.7% at every level, which validates the harness and the
box; our stack is 23-35% behind; and production's forty tuned knobs change nothing on our stack, so the gap is
code, not configuration. At 6 streams and 262,144 tokens our stack also refuses to boot on its per-stream
memory estimate.

For scale, on the earlier sweep at bf16 and 131,072 tokens our stack measured 49.3 / 82.3 at one stream against
stock v1.2.6's 50.3 / 71.2, i.e. the levers we did port are worth about 15% on code decode, while production
sits 57% above stock. The missing 40 points are levers production has that our tree does not.

## Why: production is a different engine, with ~93 knobs ours does not have

Production runs the ai-engine tree at `e5139fc` (image label `ai-engine.src-sha256`). Our fork's `main` is that
stack (`27b6700c`); our v1.2.6 tree is upstream `6e9af930` plus the 30 patches. Comparing the two:

- knobs: 101 in production, 71 in ours, 93 unique to production;
- structure: production's Flash Next is 109 files with large modules (`cuda_engine.zig`, `cuda_forward.zig`,
  `cuda_native.zig`, `cuda_int4.zig`, `cuda_mtp_q4.zig`, `cuda_fp8.zig`, `cuda_ngram.zig`); v1.2.6 is 585 files
  with per-kernel units.

So this is not a cherry-pick: each production lever has to be re-implemented against v1.2.6's structure. The
lever map below is the port backlog, generated by mapping every production-only knob to the code it gates.

The decode-critical clusters, in the order they should be attempted:

1. **Draft and MTP**: `TF_FLASHNEXT_DRAFT_INT4`, `TF_FLASHNEXT_MTP_FP8`, `TF_FLASHNEXT_MTP_Q4` (and `_MSE`),
   `TF_FLASHNEXT_DRAFT_DEPTH_SHARED`, `TF_FLASHNEXT_DRAFT_CONTINUE`, `TF_FLASHNEXT_DRAFT_PROPOSE`,
   `TF_FLASHNEXT_HEAD_ROW_TILES`, `TF_FLASHNEXT_INT4_TILE`, `TF_FLASHNEXT_INT4_PROMPT_DOWN`,
   `TF_FLASHNEXT_INT4_PROMPT_GATE_UP`. This is where most of production's decode headroom plausibly lives: a
   4-bit/FP8 drafter proposes more tokens per round than our bf16 draft head.
2. **Round scheduling**: `TF_FLASHNEXT_DEPTH`, `TF_FLASHNEXT_BATCH_DRAWS`, `TF_FLASHNEXT_BATCH_WINDOWS`,
   `TF_FLASHNEXT_EARLY_DRAW`, `TF_FLASHNEXT_DRAW_ONCE`, `TF_FLASHNEXT_FILL`, `TF_FLASHNEXT_FILL_LAYERS`,
   `TF_FLASHNEXT_DROP_PAGES`, `TF_FLASHNEXT_COST_RETIME`.
3. **FP8 kernel variants**: `TF_FLASHNEXT_FP8_LD`, `TF_FLASHNEXT_FP8_FUSED_SPLIT`,
   `TF_FLASHNEXT_FP8_FUSED_SPLIT_N`, `TF_FLASHNEXT_FP8_PROMPT_TILES`, `TF_FLASHNEXT_GLUE_FUSE`,
   `TF_FLASHNEXT_GLUE_SPLIT`, `TF_FLASHNEXT_ATTN_MULTI`, `TF_FLASHNEXT_QSA_SELECT`, `TF_FLASHNEXT_QSA_TILE`,
   `TF_FLASHNEXT_UPMIX_DECODE`, `TF_FLASHNEXT_REDUCE_ACT`.
4. **Copy window**: `TF_FLASHNEXT_COPY_MISS`, `_RAMP`, `_RESYNC`, `_RESYNC_PROMPT_ONLY`, `_SHARED`,
   `TF_FLASHNEXT_WINDOW`, `TF_FLASHNEXT_PRODUCT_STREAMS`, `TF_FLASHNEXT_SEQ_POOL`, `TF_FLASHNEXT_WARM_POOL`,
   `TF_FLASHNEXT_SOLO_MAX`. We have a copy window but nothing like production's gating of it.
5. **MoE and prompt**: `TF_FLASHNEXT_EXPERT_SHAPE`, `TF_FLASHNEXT_EXPERT_SMS_FREE`, `TF_FLASHNEXT_COUNT_EXPERTS`,
   `TF_FLASHNEXT_INT4AR_FAST`, `TF_FLASHNEXT_FP4_SERIAL`, `TF_FLASHNEXT_L2PF`, `_L2PF_BYTES`,
   `TF_FLASHNEXT_MEDIA_GRAPHS`, `TF_FLASHNEXT_COMM_PRIORITY`.
6. **N-gram**: production's `cuda_ngram.zig` / `cuda_ngram_host.zig` sit behind the same three knobs we have,
   but the implementation differs; treat it as already ported until a measurement says otherwise.

## What this means for the plan

The self-check defect (windows falling back from 48 to 32 rows, `0 of 2080`) is real, is confined to patches
0016-0030, and costs some decode, but it cannot explain 23-35%: production serves a 64-row window and our whole
rows lever is worth about 3-6% at one to two streams. The bulk of the catch-up is clusters 1 and 2 above, and
the only honest order is: fix the rows regression (it gates the copy lever), then port the drafter and round
scheduling levers, measuring each against this table.

## Where the time actually goes: the round, not the tokens a round yields

Attribution on the production tree, with production's own launcher (its binary predates `--kv-cache`, so the 1.2.6
recipe cannot boot it at all: every earlier production cell was silently measuring the already-running container).
One stream, one pass, 512 tokens, same prompts:

| arm | prose tok/s | code tok/s | prose rounds | code rounds |
|---|---|---|---|---|
| production, all levers on | 71.5 | 127.7 | 186 | 81 |
| `MTP_Q4=0` | 75.0 | 130.6 | 186 | 81 |
| `DRAFT_INT4=0` | 72.4 | 126.4 | 186 | 81 |
| `UPMIX_DECODE=0` | 75.1 | 130.5 | 186 | 81 |
| `QSA_SELECT=0` | 75.0 | 130.7 | 186 | 81 |
| `EARLY_DRAW=0` | 75.3 | 130.9 | 186 | 81 |

Every arm came out 3-5% faster than the base, including knobs that cannot plausibly help, which is the cold-boot
confound of a first boot (the n-gram tables page from disk), so no single knob is the lever. The round counts are
identical across arms, which is the useful part: those knobs change the cost of a round, not how many tokens it
yields, and none of them carries a large share of the gap.

The round economics, same prompt, one stream:

| | ms a round, prose | ms a round, code | rounds for 512 tokens, code |
|---|---|---|---|
| production | 38.5 | 49.5 | 81 |
| our v1.2.6 stack | 64.7 | 77.7 | 90 |

So production's verify round costs about 1.6x less than ours, and it needs about 10% fewer rounds. The gap is
per-round cost, which is the engine: production's `cuda_engine` / `cuda_forward` / `cuda_fp8` architecture plus the
FP8 MTP drafter overlay (`TF_FLASHNEXT_MTP_FP8` points at a separate azampatti INT4-AutoRound-derived drafter weight
set that our tree does not load at all). That is what has to be ported, and it is where the levers of cluster 1 and 2
land.

## The 262,144-target memory refusal

Our stack refuses 6 streams at 262,144 tokens: "`--parallel 6 needs 30.23 GiB for its streams at a 262144-token
window, and the CUDA memory budget leaves 27.27 GiB`", i.e. 5.04 GiB a stream. Production serves 8 streams in
25.61 GiB, 3.20 GiB a stream. Measured:

- switching drafting off (`TF_FLASHNEXT_DRAFTS=0`) leaves the estimate at 30.23 GiB, unchanged: the budget is
  computed from the loaded draft head (`cuda_lanes_load.streamBytes` adds `mtp.Draft.bytes(window, head_ids, ...)`
  whenever a head is present), so the drafts flag does not enter it;
- the sequence alone, from `cuda_seq_bytes.seqBytesFor` at fp8 and 262,144 tokens, is about 3.21 GiB a stream:
  36 DeltaNet layers of conv tails and fp32 states (0.11 GiB), 12 attention layers at 1,056 bytes a position a
  layer (3.09 GiB), pooled indexer blocks (0.02 GiB).

So of the 5.04 GiB priced a stream, about 3.21 is the sequence and roughly 1.8 is the draft head's caches plus the
draft pass's own arrays (`cuda_mtp_draft.zig`'s `bytes`: two bf16 head caches at the full window, the indexer keys,
the pooled blocks, the logits, the saved states and the per-layer state). Production does not pay that at bf16: its
drafter runs the FP8 MTP overlay. Half of 1.8 GiB takes a stream to about 4.1 GiB, and 6 streams to 24.8 GiB, which
fits the 27.27 GiB budget.

Two fixes follow, in expected value order: price and serve the draft head caches in fp8 (the port of production's
`TF_FLASHNEXT_MTP_FP8`, cluster 1), or size them to the window the serve actually accepts rather than the full
context. Neither is done yet, and the split between "draft caches" and "draft arrays" above is arithmetic from the
sizing functions, not an instrumented measurement: the next step is one boot that prints `streamBytes`' parts.

## The FP8 drafter port, scoped against what v1.2.6 already has

Production's drafter lever is `TF_FLASHNEXT_MTP_FP8`, an overlay directory of the MTP layer's linears on block FP8
(`tools/mtp_fp8.py` builds it). Its patch upstream is 50 lines across two files: an `overlay2` option on the weight
loader and one condition that makes the MTP layer's attention weights load through the block-FP8 path.

What v1.2.6 already carries: an FP8 experts loader (`cuda_fp8_experts_load.zig`) whose tests load the MTP layer's
experts by name (`language_model.mtp.layers.0.mlp`), and FP8 KV with 1,056 bytes a position a layer. What it does
not carry: any `int4ar` / overlay plumbing at all (28 files mention fp8; none of them has an overlay), and the MTP
layer's attention linears load as 4-bit affine like the rest of the body.

So the port is three commits, in this order:

1. **Price the draft head caches by their own format.** `cuda_mtp_draft.zig`'s `bytes` assumes bf16 head caches; with
   an fp8 head the same stream drops by roughly 0.9 GiB, which is what puts six streams at 262,144 inside the
   budget. This is memory only and does not touch kernels.
2. **Load the MTP layer's attention linears in FP8.** The experts half exists; this is the attention half, plus the
   overlay-directory plumbing if we want the weights in a separate directory rather than the checkpoint.
3. **Measure it as an artifact**: the same cells as the table at the top of this document, plus the round economics,
   because the whole point of the drafter lever is a cheaper round (production 49.5 ms a code round against our
   77.7 ms).

Nothing of this is done yet. The diagnostic phase of the catch-up is complete: the gap is measured, its mechanism is
the cost of a round, the levers that carry it are enumerated by knob and file, the memory refusal is explained, and
the rows regression is localised to patches 0016-0030 with the read-out, tile, chunk, HC and copy knobs excluded.

## Correction (2026-11-11 evening): the evaluation ran in the wrong order, and the stack was never the sum of its patches

The owner's procedure was: stock with no patches, then environment tuning on stock, then our patches added one at a
time. Everything above this section did the reverse: it started from the full 30-patch stack and subtracted. Two
consequences make the earlier tables unsafe as verdicts:

1. **Every "baseline" was the patched stack with our levers already on.** The campaign recipe (`scripts/config.sh` of
   the unmodified MiaAI recipe checkout) exports seventeen lever defaults, eleven of them ours (`GATHER_READ=pread`,
   `PROMPT_HC2=1`, `PROMPT_SHARED_DIRECT=1`, `PROMPT_GEMM2=1`, `HEAD_PIECE=1536`, ...). So arms such as `hc2on` or
   `PROMPT_GEMM2=0` were not what their names say, and "inert" above means "inert on top of everything else".
2. **The old series only compiled at 0005, 0012, 0015 and 0030**, so no lever after 0015 was ever tested alone. The
   reasons are blind-port damage, found by reading the intermediate trees:
   - `0030` (the "integration tail") reset `cuda_mtp_draft.zig` and `cuda_mtp_ops.zig` to upstream to undo kv8's
     broken draft-cache sizing (one fp8 row where the window's rows belong). Seven patches touch those files, so the
     reset also deleted the rows lever's window guards (0001, 0005), the n-gram draft-ahead argument (0013), the
     4-bit draft head (0020) and the read-out pieces (0022). The "full stack" was therefore missing parts of four
     levers, which is the likeliest cause of the self-check reading 0 of 2,080 only with the full series;
   - `0018` defines `promptGemm2` twice; a later patch deletes one copy;
   - `0022` wrote merge-tool residue (`22: @both`, `23: @both`, `24: @both`, `25: @both`) over real lines in the test
     registry and the changelog; `0027` repaired the registry in passing.

The rework (`scripts/qwen38/zig/target/mkrung.sh` + `overlay.py`): each rung tree is pristine `6e9af930` plus the old
patches through that lever, with the repair applied where the damage happens: `0012b` makes kv8 leave the draft head
bf16 without touching the other levers' hunks, the duplicate knob is removed at 0018, the residue at 0022, and the
tile-kernel fields move from the tail to the read-out lever. Eleven rungs assemble (0005, 0012, 0015, 0017, 0019,
0021, 0025, 0026, 0027, 0029, 0032), each exported as one cumulative patch for the box to build.

The measurement now runs in the stated order (`buildup.sh`): stage 1 stock, stage 2 one upstream knob per arm on
stock, stage 3 one rung at a time against the rung before it, at bf16 and 131,072 tokens because the pristine engine
cannot hold four bf16 windows of 262,144.

### Why the read-out rung faulted, and why the old full stack read 0 of 2,080

Old patch 0022 was cut against an older tree. Besides its own feature it carries three reversions of the 1.2.6 base,
all of which apply cleanly and compile:

| what 0022 took back | file | effect |
|---|---|---|
| `self.pos0 = pos0;` in `Pass.chunk` | `cuda_batch.zig` | a chunk runs at the position the last caller left: the window self-check reads 0 of 2,080 |
| `if (last) d.prompt_last = ...` in `prefillChunk` | `cuda_mtp_ops.zig` | the first draft reads address 0: `CUDA_ERROR_ILLEGAL_ADDRESS` on the first request |
| `TF_FLASHNEXT_PROMPT_MX128` default back to 1024 | `cuda_knobs.zig` | the relaxed (inexact) prompt tile on by default, which 0017 had switched off |

The old tail (0030) restored the second and the third and never the first. So the old full stack served, with every
prompt chunk at a stale position, and that is the `0 of 2080` it showed; the head-to-head numbers at the top of
this document were measured on that stack. `overlay.py` repairs all three at rung 22.

### A gate for this class, and what it found next

`scripts/check-patch-reverts.py` reads a series in order and reports a line an earlier patch added being removed, a
line an earlier patch removed coming back, and a base code line deleted with nothing resembling it added. On the old
series it reports 328 findings, the three above among them. On the 13-lever series cut from the rung trees it
reported 32, and two of those were real, both in old 0013 (the n-gram row cache):

- **`Ngram.fill` was merged wrong, on the path every n-gram row takes.** The base chooses its reader with
  `if (g.read_mode == .pread) readers.read() else ... tables.gather()`. The patch put its hook in place of that test:
  `if (!try ple_cache.row(...)) readers.read() else ... tables.gather()`. So a row the row cache had filled was then
  gathered again from the mapping (the work done twice, and the mapping touched, which the cache exists to avoid),
  and a row it had not filled went to the positional reader whatever `TF_FLASHNEXT_PLE_IO` said. Every measurement
  of the n-gram lever so far, the 1.3% loss in the ladder included, is a measurement of that. Upstream 1.2.6 also
  already has its own positional reader, on by default on Linux, so "pread" as such is no longer ours.
- `Ngram.deinit` lost `g.waitWarm()` and the destroy of the gather pool (teardown only).

`overlay.py` repairs both at rung 13 (`ple: the row cache goes in front of the base's reader choice`), the series
replays onto pristine to the last rung's exact tree, and the repaired accepted rung is image `g21`.

Two tools came out of this stretch and are in `AGENTS.md`: the tree's own
`zig build compile-config-server -Dtarget=aarch64-linux-gnu` type-checks a patched tree on the laptop in minutes
(every rung is now compiled there before the box builds it), and `mkladder.sh` cuts the whole ladder, the additive
series and the gate report in one command.

| part | checkpoint | read by | one launch | rate of one launch |
|---|---|---|---|---|
| mixer, widest projection (`in_proj_qkv` / `q_proj`) | 26.2 / 31.5 MB, MXFP8 (1 byte a weight) | 48 launches a round | 188.6 us | 139 to 167 GB/s |
| mixer, out projection | 15.7 MB, MXFP8 | 48 launches a round | 84.4 us | 186 GB/s |

| routed experts (512 a layer, 10 a token, 2.6 MB each) | 65.8 GB in all, 4-bit | the experts the rows pick | | |

The checkpoint holds 3.04 GB of mixers and 1.32 GB of hyper-connections (97 read-outs, a down and an up each), and a
verify window walks all of both; the head's draft passes walk the head layer's again, which is why the read-outs
launch more than 97 times a round.

Two things stand out, and neither is a missing knob.

1. **The hyper-connections are a quarter of the round and the checkpoint stores them in BF16.** Production's
   checkpoint (`azampatti/...INT4-AutoRound`) carries a `fast-fp8` copy of exactly these matrices, 3.28 MB each in
   E4M3 where NVIDIA's FP4 checkpoint has 6.55 MB in BF16, and production's loader takes that copy when it is there
   (`cuda_weights.zig`, "the fast-fp8 variant: down and up on block FP8"). The mixers are 8-bit in both checkpoints
   and the experts 4-bit in both. So of the 18.7 ms (prose) and 14.8 ms (code) between our round and production's,
   the read-outs' bytes are the one difference of format: half the bytes of a part that costs 15.4 ms a round
   (10.67 up, 4.73 down).
2. **The UP read-out reads at half the rate of everything beside it.** Same lane kernel, 160 blocks of 64 output
   columns over a K of only 320: 71 GB/s, against 139 to 186 GB/s for the mixers and 155 for its own DOWN.

The 12-bit lossless copy of these matrices (old 0026, `TF_FLASHNEXT_HC_Q12`) aimed at the same bytes and measured
flat on 1.2.4; it is off by default, so the ladder's q12 row above only shows that carrying it costs nothing.

### A lever for the first of those: the read-outs in MXFP8 (`TF_FLASHNEXT_HC_MXFP8`)

`cuda_hc_mxfp8.zig`, on the repaired accepted rung (image `gm21`): at load, each hyper-connection matrix is
re-coded from BF16 to MXFP8, the format the checkpoint's own mixers use (E4M3 codes, one power-of-two scale a row's
32 inputs, chosen so the group's largest weight lands at 448 or under and no code saturates), and uploaded through
the engine's existing MXFP8 projection, so the read-outs run on the kernels the mixers already run on. Default off;
off, the loader is untouched. **It is not exact**: E4M3 keeps three mantissa bits where BF16 keeps seven, so replies
can differ from stock's, the same trade production's `fast-fp8` copy makes. Its host test (the scale rule, every
code within an eighth of its weight, no saturation) runs in the family's suite and was proven to fail on a planted
defect before it was trusted.

Measured on one binary (`gm21`, bf16, 131,072, `mx.sh`), aggregate tok/s prose / code:

| streams | off | on | change |
|---:|---|---|---|
| 1 | 61.5 / 81.4 | 63.7 / 86.7 | +3.5% / +6.5% |
| 4 | 113.1 / 166.2 | 116.7 / 175.1 | +3.1% / +5.3% |

Golden 6/6 with it on, but the 512-token replies take a different number of rounds (149 against 146 prose, 91

**Half tiles for the up read-out: no gain, not kept.** The engine already runs a decode projection on its 32-column

## Knob sweep on the new engine (step one: tune what already exists)

The new tree carries 68 `TF_FLASHNEXT_*` knobs that production's launcher never sets. Swept at the target's settings,

## Runbook: reproducing the per-lever evaluation

(`~/work/lanes/rpr/recipe`), one fresh boot a cell, `MEM_CHECK=0` because the host-memory precheck refuses a
262,144-token window on this box, and a clean `docker rm -f` plus a lock removal first when a previous run was
interrupted (`~/.local/state/qwen38-flash-next-tf/start.lock`).

```
# one arm: a fresh boot, golden, one decode pass a kind, the boot self-check, then stop
IMG=tensorfold-qwen38:stack126v2 bash ~/work/target/patcheval.sh "<armname>:<ENV KNOBS>"

# the recipe gate wants tf.kernels=embedded on anything this table measures
bash ~/work/lanes/fp4port/relabel.sh tensorfold-qwen38:<tag> embedded
```

Rules that the measurements depend on, each learned the hard way here: discard a warm-up arm and compare against a
warm baseline (a first boot is 1.4-2.0% cold on code and 5.5-6.0% on prose, the tables paging from disk); run the A/B/A
when a delta is small enough to matter; compare replies with `python3 ~/work/zgold_cmp.py <ref> <arm>` and demand 6/6;
and never read a production-image cell as a fresh boot, because that image's binary predates `--kv-cache` and the
recipe refuses it, so `docker logs` will be the container that was already running.

## What production does to the decode read-outs, and the levers that follow from it (2026-11-12)

The round's kernel table above says the decode round is 62.58 ms in 1,586 launches, and that one kernel, the
hyper-connection UP read-out, is 10.67 ms of it in 115.9 launches of 92.0 us, reading 6.55 MB of BF16 weights each
time at 71 GB/s where every other dense kernel in the table reads at 139 to 186. That row, and the 4.73 ms DOWN
read-out beside it, are what production's own launcher and boot log aim at.

**Production's boot log, not inference** (a production-stack server log kept on spark6,
`~/work/q25/out/serverlog-ttft-p3B-20261023-022614.log`, and `production/qwen6-start-prod.sh` on the `production`
branch):

```
info: hc q12: decode read-outs from 12-bit copies: 192 matrices, 1266.2 -> 970.8 MB, 95876 escapes
info: decode read-outs: up projection and mix in one pass (_hc_up_mix BM 32)
info: decode read-outs: _reduce and _hc_act in one launch (tf_fn_hc_reduce_act_kernel, checked against the kernel set at load)
info: copy windows: a lone stream verifies up to 64 rows (TF_FLASHNEXT_WINDOW; the MTP chain 16)
```

So production's decode read-out is: the down and up matrices read from a lossless 12-bit copy (`TF_FLASHNEXT_HC_Q12=1`
in its launcher, 1,266 MB of BF16 rows down to 971 MB), the reduce and the activation in one kernel, and the up
projection fused with the stream mix. It does not use the checkpoint's `fast-fp8` copies: that path needs
`TF_FLASHNEXT_INT4AR_FAST`, which the production launcher never sets, so the earlier reading of the gap as "their
read-outs are fp8 bytes and ours are bf16" is wrong. Their read-outs are the same BF16 numbers as ours, stored in
12 bits and walked by fewer, wider kernels.

### Rank 1 measured and rejected: the wide tile moves the launches and costs 6% (patch text kept out of the series)

`TF_FLASHNEXT_DECODE_WIDE=N` (our patch text, `work/0014-decode-wide-tile.patch`) lets a BF16 native projection of
N rows or more take the 128-column tile the prompt passes already use, with `TF_FLASHNEXT_DECODE_WIDE_K32=0` for
that tile's K64 instance. Image `v14` is v1.2.7 plus the 13 levers plus that patch; every arm below is the same
binary with the switch off and on, one fresh boot a cell, bf16 KV, 131,072 tokens, `HOST=127.0.0.1`
(`scripts/qwen38/zig/target/widetile.sh`, spark6 `~/work/target/widetile.log`, cells under `bench/pe-wt*/`):

| off | 60.8 / 80.4 | 86.5 / 119.2 | 111.7 / 165.0 | 144.7 / 202.3 | 146 / 89 | 1176 of 2080 |
| on | 60.5 / 79.9 | 86.0 / 119.0 | 111.2 / 164.8 | 143.9 / 201.3 | 146 / 89 | 1176 of 2080 |
| off again | 60.7 / 80.1 | | 111.7 / 164.4 | | 146 / 89 | 1176 of 2080 |

It is exact and it is not a win: every decode reply hash matches the off arm's (10 of 10 at C=1 and C=4, 16 of 16
at C=2 and C=6), the rounds a 512-token reply takes are the same, golden is 6/6, and the serve is 0.3 to 0.6%
slower everywhere. The kernel log says why (image `v14k`, the same tree with the round and kernel logs,

| arm | the BF16 read-out launches | round |
|---|---|---|

The launches did move to the 128-column tile, and every other row of the table is unchanged to within 0.1 ms, so
the lever does exactly what it says and the shape is simply not where the time is. The round log agrees: the verify
forward is 50.49 ms off and 51.40 on at 4.75 rows, 55.95 and 55.91 at 6.86. The patch is not in `patches/1.2.7`.

### Why it could not have won: the 71 GB/s read-out was an average over two different kernels

The kernel table books time by kernel, and every BF16 lane call of 64-column blocks lands on one symbol. The
half-tile arm (`TF_FLASHNEXT_HALF_BELOW=161`, image `gmh21`) splits that bucket, because only launches of fewer
than 161 column blocks take the half tile. One stream, the code prompt, against the same arm of the baseline image
`gk21b`:

| arm | `qmmf<BF16,16,32>` | `qmmf<BF16,16,64>` | both |
|---|---|---|---|
| baseline | - | 122.5 launches, 93.1 us, 11.402 ms | 11.402 ms |
| half tile | 115.3 launches, 36.9 us, 4.255 ms | 7.1 launches, 998.2 us, 7.112 ms | 11.367 ms |

So the hyper-connection read-outs are 115 launches of about 37 us, which is 6.55 MB at 177 GB/s, the same rate as
everything else dense in the table: there is no headroom in them at all, and the "71 GB/s" of the earlier table was
115 read-outs at the roofline averaged with about 7 launches of something else at a millisecond each. Those seven
are the hidden row: 7 launches of about 1 ms is 6 to 7 ms of a 63 ms round, and they scale with the draft passes,
not with the layers.

They are the MTP layer's own BF16 weights. The NVFP4 checkpoint quantises the backbone but leaves the drafter's
linears in BF16: reading the headers of `nvidia/Qwen3.8-Flash-Next-FP4-Local`, the `mtp.*` tensors hold **181.1 MB
of BF16** (`self_attn.q_proj` 62.9 MB, `self_attn.o_proj` 31.5, `fc_embedding` and `fc_hidden` 13.1 each, the
drafter's own four hyper-connection matrices 6.55 each, the shared expert 3.28 each) beside 1,258 MB of 4-bit
expert words. Every draft pass walks them. That is what production's `TF_FLASHNEXT_MTP_FP8` overlay replaces (its
boot log names the file: `overlay /root/.cache/huggingface/ots-mtp-fp8/mtp-fp8.safetensors`), and what
`TF_FLASHNEXT_MTP_Q4` does in the engine; our patch 0007 already did the same thing to the drafter's head alone and
that one change is worth 11.6% prose and 8.1% code at one stream.

**So the next lever, and the largest one left, is the drafter's linears in 8 or 4 bits.** It is exact in the sense
this campaign uses, the same sense patch 0007 is exact: a draft is only a proposal, the verify forward decides every
token, and a reply's text is unchanged while the rounds it takes move. Ranked against it, the read-out levers above
(q12's 23% of 1,266 MB, the fused up and mix, the write-back's normalize) are all smaller.

### Rank 2 measured and rejected: the 12-bit read-out copies buy nothing here

`TF_FLASHNEXT_HC_Q12=1`, patch 0009's lever and a setting production's launcher carries, on the same binary
(image `v14`, `scripts/qwen38/zig/target/wt2chain.sh`, spark6 `~/work/target/widetile2.log`):

| arm | C=1 | C=4 | rounds prose/code | self-check |
|---|---|---|---|---|
| off | 61.3 / 81.1 | 111.8 / 164.4 | 146 / 89 | 1176 of 2080 |
| `HC_Q12=1` | 61.1 / 81.3 | 111.7 / 164.0 | 146 / 89 | 1176 of 2080 |
| `HC_Q12=1` with the wide tile | 61.3 / 80.7 | 112.0 / 164.3 | 146 / 89 | 1176 of 2080 |

It engages and it is lossless: the boot line is "read-outs in 12 bits: 194 matrices, 1.07 GB beside their rows
(76.2% of them), 99304 escapes", the per-boot check compares the copy's product with the BF16 lane's at 1, 5, 16,
17 and 32 rows in both output kinds, and all ten decode reply hashes match the off arm's. It is also flat, within
0.3% everywhere, which is what the corrected attribution predicts: 24% off the bytes of a group that already runs
at 177 GB/s and holds 9 ms of a 63 ms round cannot be worth more than about 2 ms, and the 12-bit unpacking takes
that back. The default stays off; the lever stays in patch 0009 for a box where the copies matter.

Two levers in a row under 1%, so the read-out family is closed. The measured state of the stack against the target
is in `patches/1.2.7/README.md`, and the next lever is the drafter's BF16 linears named above.

### The glue group, first lever: the fused write-back at a decode window is slower and not exact

`cuda_batch_hc.fuses` takes the write-back that also writes the read-out's normed rows only from 64 rows up, so a
decode window of 5 runs the write-back and the normalize as two launches (`fn_hc_normalize_cols`, 110.5 launches,
6.9 us, 0.760 ms a round). Patch text `work/0015-hc-fuse-rows.patch` makes that floor a knob,
`TF_FLASHNEXT_HC_FUSE_ROWS`, default 64. Image `v18`, one binary, bf16 KV, 131,072, one fresh boot a cell
(`scripts/qwen38/zig/target/gluechain.sh`, spark6 `~/work/target/glue.log`):

| arm | C=1 | C=4 | rounds prose/code | replies against the warm arm |
|---|---|---|---|---|
| floor 64 (default) | 62.9 / 86.8 | 112.8 / 170.7 | 144 / 86 | 10 of 10 identical |
| floor 1 | 57.9 / 74.1 | | 145 / 105 | 2 of 2 different |

Two findings, and the second matters more than the first. It is 8% slower on prose and 15% on code, which the
kernel's shape predicts: the fused form is one block a row, so five rows fill five of the box's 48 SMs where the
two launches fill 50 and 200. And it is NOT exact at decode row counts: the replies differ, so the file's "the
same bits either way" holds at the prompt row counts it was measured on and not at a five-row window. The floor
stays at 64 and the patch is not in the series; the comment should be read as a claim about prompt passes.
