# Catching up with the production stack on TensorFold v1.2.6

Measured on spark6 on 2026-11-11, one fresh boot a cell, the target's own settings (nvfp4 checkpoint, fp8 KV,
262,144-token windows, every slot busy, 512-token requests, three passes, median).

## The gap, measured

| arm | 1 stream prose / code | 2 | 4 | 6 |
|---|---|---|---|---|
| target document (production, older stack) | 70.9 / 113.0 | 103.3 / 173.7 | 162.3 / 254.0 | 202.2 / 311.8 |
| production image on this box today | 70.4 / 112.1 | 104.3 / 173.7 | 165.1 / 254.8 | 204.9 / 312.3 |
| v1.2.6 with all 30 patches, defaults | 54.6 / 78.6 | 69.8 / 115.7 | 108.6 / 164.8 | will not boot |
| the same stack with production's whole env | 51.9 / 79.1 | - | 109.6 / 165.4 | - |

So: production reproduces the target document within 1.7% at every level, which validates the harness and the
box; our stack is 23-35% behind; and production's forty tuned knobs change nothing on our stack, so the gap is
code, not configuration. At 6 streams and 262,144 tokens our stack also refuses to boot on its per-stream
memory estimate.

For scale, on the earlier sweep at bf16 and 131,072 tokens our stack measured 49.3 / 82.3 at one stream against
stock v1.2.6's 50.3 / 71.2, i.e. the levers we did port are worth about 15% on code decode, while production
sits 57% above stock. The missing 40 points are levers production has that our tree does not.

## Why: production is a different engine, with ~93 knobs ours does not have

Production runs the ai-engine tree at `e5139fc` (image label `ai-engine.src-sha256`). Our fork's `main` is that
stack (`27b6700c`); our v1.2.6 tree is upstream `6e9af930` plus the 30 patches. Comparing the two:

- knobs: 101 in production, 71 in ours, 93 unique to production;
- structure: production's Flash Next is 109 files with large modules (`cuda_engine.zig`, `cuda_forward.zig`,
  `cuda_native.zig`, `cuda_int4.zig`, `cuda_mtp_q4.zig`, `cuda_fp8.zig`, `cuda_ngram.zig`); v1.2.6 is 585 files
  with per-kernel units.

So this is not a cherry-pick: each production lever has to be re-implemented against v1.2.6's structure. The
lever map below is the port backlog, generated by mapping every production-only knob to the code it gates.

The decode-critical clusters, in the order they should be attempted:

1. **Draft and MTP**: `TF_FLASHNEXT_DRAFT_INT4`, `TF_FLASHNEXT_MTP_FP8`, `TF_FLASHNEXT_MTP_Q4` (and `_MSE`),
   `TF_FLASHNEXT_DRAFT_DEPTH_SHARED`, `TF_FLASHNEXT_DRAFT_CONTINUE`, `TF_FLASHNEXT_DRAFT_PROPOSE`,
   `TF_FLASHNEXT_HEAD_ROW_TILES`, `TF_FLASHNEXT_INT4_TILE`, `TF_FLASHNEXT_INT4_PROMPT_DOWN`,
   `TF_FLASHNEXT_INT4_PROMPT_GATE_UP`. This is where most of production's decode headroom plausibly lives: a
   4-bit/FP8 drafter proposes more tokens per round than our bf16 draft head.
2. **Round scheduling**: `TF_FLASHNEXT_DEPTH`, `TF_FLASHNEXT_BATCH_DRAWS`, `TF_FLASHNEXT_BATCH_WINDOWS`,
   `TF_FLASHNEXT_EARLY_DRAW`, `TF_FLASHNEXT_DRAW_ONCE`, `TF_FLASHNEXT_FILL`, `TF_FLASHNEXT_FILL_LAYERS`,
   `TF_FLASHNEXT_DROP_PAGES`, `TF_FLASHNEXT_COST_RETIME`.
3. **FP8 kernel variants**: `TF_FLASHNEXT_FP8_LD`, `TF_FLASHNEXT_FP8_FUSED_SPLIT`,
   `TF_FLASHNEXT_FP8_FUSED_SPLIT_N`, `TF_FLASHNEXT_FP8_PROMPT_TILES`, `TF_FLASHNEXT_GLUE_FUSE`,
   `TF_FLASHNEXT_GLUE_SPLIT`, `TF_FLASHNEXT_ATTN_MULTI`, `TF_FLASHNEXT_QSA_SELECT`, `TF_FLASHNEXT_QSA_TILE`,
   `TF_FLASHNEXT_UPMIX_DECODE`, `TF_FLASHNEXT_REDUCE_ACT`.
4. **Copy window**: `TF_FLASHNEXT_COPY_MISS`, `_RAMP`, `_RESYNC`, `_RESYNC_PROMPT_ONLY`, `_SHARED`,
   `TF_FLASHNEXT_WINDOW`, `TF_FLASHNEXT_PRODUCT_STREAMS`, `TF_FLASHNEXT_SEQ_POOL`, `TF_FLASHNEXT_WARM_POOL`,
   `TF_FLASHNEXT_SOLO_MAX`. We have a copy window but nothing like production's gating of it.
5. **MoE and prompt**: `TF_FLASHNEXT_EXPERT_SHAPE`, `TF_FLASHNEXT_EXPERT_SMS_FREE`, `TF_FLASHNEXT_COUNT_EXPERTS`,
   `TF_FLASHNEXT_INT4AR_FAST`, `TF_FLASHNEXT_FP4_SERIAL`, `TF_FLASHNEXT_L2PF`, `_L2PF_BYTES`,
   `TF_FLASHNEXT_MEDIA_GRAPHS`, `TF_FLASHNEXT_COMM_PRIORITY`.
6. **N-gram**: production's `cuda_ngram.zig` / `cuda_ngram_host.zig` sit behind the same three knobs we have,
   but the implementation differs; treat it as already ported until a measurement says otherwise.

## What this means for the plan

The self-check defect (windows falling back from 48 to 32 rows, `0 of 2080`) is real, is confined to patches
0016-0030, and costs some decode, but it cannot explain 23-35%: production serves a 64-row window and our whole
rows lever is worth about 3-6% at one to two streams. The bulk of the catch-up is clusters 1 and 2 above, and
the only honest order is: fix the rows regression (it gates the copy lever), then port the drafter and round
scheduling levers, measuring each against this table.

## Where the time actually goes: the round, not the tokens a round yields

Attribution on the production tree, with production's own launcher (its binary predates `--kv-cache`, so the 1.2.6
recipe cannot boot it at all: every earlier production cell was silently measuring the already-running container).
One stream, one pass, 512 tokens, same prompts:

| arm | prose tok/s | code tok/s | prose rounds | code rounds |
|---|---|---|---|---|
| production, all levers on | 71.5 | 127.7 | 186 | 81 |
| `MTP_Q4=0` | 75.0 | 130.6 | 186 | 81 |
| `DRAFT_INT4=0` | 72.4 | 126.4 | 186 | 81 |
| `UPMIX_DECODE=0` | 75.1 | 130.5 | 186 | 81 |
| `QSA_SELECT=0` | 75.0 | 130.7 | 186 | 81 |
| `EARLY_DRAW=0` | 75.3 | 130.9 | 186 | 81 |

Every arm came out 3-5% faster than the base, including knobs that cannot plausibly help, which is the cold-boot
confound of a first boot (the n-gram tables page from disk), so no single knob is the lever. The round counts are
identical across arms, which is the useful part: those knobs change the cost of a round, not how many tokens it
yields, and none of them carries a large share of the gap.

The round economics, same prompt, one stream:

| | ms a round, prose | ms a round, code | rounds for 512 tokens, code |
|---|---|---|---|
| production | 38.5 | 49.5 | 81 |
| our v1.2.6 stack | 64.7 | 77.7 | 90 |

So production's verify round costs about 1.6x less than ours, and it needs about 10% fewer rounds. The gap is
per-round cost, which is the engine: production's `cuda_engine` / `cuda_forward` / `cuda_fp8` architecture plus the
FP8 MTP drafter overlay (`TF_FLASHNEXT_MTP_FP8` points at a separate azampatti INT4-AutoRound-derived drafter weight
set that our tree does not load at all). That is what has to be ported, and it is where the levers of cluster 1 and 2
land.
