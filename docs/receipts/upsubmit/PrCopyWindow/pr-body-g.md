## What this changes

Before, a verify window on Flash Next CUDA carries at most 32 rows, so a lone stream's copy window ramps to at most 31 copied tokens a round whatever the machine's rows actually do. After, with `TF_FLASHNEXT_WINDOW_CHECK=1` (default off) a load measures, before it serves, the widest verify window whose every row's scores equal the scores of a one-token step on that machine, and the copy window grows to that width, past the 32 rows served without the switch and at most the 48 rows a window's pending-row log holds. A check that cannot run, fails, or proves nothing past 32 rows leaves the window at 32, so no width past the shipped one is served unproved. With the switch off every buffer the window sizes is main's too, so the off state is exactly main.

Why a check rather than a constant: whether a 40- or 48-row window's rows equal their one-token steps is a property of the kernels and the driver on that machine, not of the model, and a change that moves a chunk position can take it away. The width is therefore measured at every boot that turns the switch on, and the check's log line names both the rows it compared and the width it serves.

The 48 is not a tuning choice: a drafted window's rows are its stream's pending-row log, which holds 48 rows and is where a partly kept window's rows stay for the next window's chain. A window wider than that would overwrite its own kept rows, so the widest window is the log's own capacity, and nothing wider is measured or served.

Why a wider window cannot change the tokens, from the code: a copy window's rows are the pending token and the copied tokens, verified in one forward (`cuda_lanes.zig` `verifyFn` builds `row_ids = [pending, copies...]`, and a lone stream takes `Ops.verify`), each row's scores landing in `Draft.logits` row by row; the lane core then commits a path in which each kept row's target sample equals that row's proposal (`accept.acceptPath`), and the committed token is `accept.targetPick`, the target's own pick and never the proposal. A reply is therefore a run of target samples at successive positions, and a copied or drafted token only decides how many rows are proposed and which can be kept. That makes a width exact or not exactly when each row's scores are the ones a one-token step produces at that position, and that is what the check measures: it builds a greedy continuation from a synthetic 96-token prompt, takes every row's one-token step scores as the reference, then for every width from 1 to 48 resets the sequence, re-runs the same prompt, checks the first drawn token is the same, runs one window of that width over the same continuation, and compares each downloaded row with its reference byte for byte over the whole u16 vocabulary row. `probeServed` logs the count and the first differing width and returns the largest width whose every row matched. A window of width W at most the proved width thus gives the same scores, the same target samples and the same accepted path as the 32-row arm for the same prefix; what changes is tokens a round, not tokens. The draw is keyed by the row's scores, the token map and the position (`cuda_mtp.drawRow` to `lanes.sampling.choose(..., position, ...)`), never by a running generator.

No GPU kernel is new or changed. A 48-row window runs the same row-by-row DeltaNet path a 32-row window runs today (`late.front` and `late.chain` when the window keeps a rollback), and the fused path, which needs 64 or more rows, is still not reached by any window. The kernel contract of those two late-log kernels (`zig/tests/cuda/contract_flashnext_late.zig`) now serves the log's 48 rows as well as 1, 9 and 32, so its gates run the widest window against the kernels they replace.
