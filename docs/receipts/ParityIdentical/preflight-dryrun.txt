The two int4tile64 runs were refused by the recipe's own state lock because a serve was starting at that
moment on the box (the other lane's window); the window's real boots hold the GPU lock and stop whatever
serves first, so the lock is free. Its wiring is proved two other ways:
  - neither launcher's exec list names TF_FLASHNEXT_INT4_TILE (grep: 0 hits in ~/qwen6-start.sh and
    ~/qwen6-start-prod.sh), while an identical override (TF_FLASHNEXT_CHUNK=2048/CHUNK_SOLO=2048) passed
    the same dry run, so the forwarding path is proven;
  - both engines read the name: P cuda_int4.zig:148, D cuda_int4.zig:151.

A REAL CATCH: the HEAD_ROW_TILES arm was a null arm. Both launchers pin it in their own exec env
  ~/qwen6-start.sh:87  TF_FLASHNEXT_HEAD_ROW_TILES=2
  ~/qwen6-start-prod.sh:54 TF_FLASHNEXT_HEAD_ROW_TILES=2
so an exported override cannot reach either engine, and the arm would have measured nothing. It is replaced in
the window by TF_FLASHNEXT_INT4_TILE=64 on both arms (the 64-pair prompt tile, which both engines claim is
bit-equal to the 16-pair one: P cuda_int4.zig:146, D cuda_int4.zig:149).
